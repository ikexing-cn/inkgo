# Agent Note: 核心以外的功能做成扩展模块，为外部插件留出接口

Status: proposed

## Problem

2026-11-02 作者提出：维护一个插件目录，除了编辑器和目录（章节树），其余功能都做成插件，插件能新增、修改界面和功能。往后想给外部开发者提供 MCP（或别的）服务，让他们用 AI 写「nice for self」的插件；这样也更容易守住架构和基建。约束是 mygo 作者说过以后会出一套基于脚本语言的动态插件方案，到时要能接进来。mygo 0.7.4 的源码、文档和 issue 里都还没有这套方案，所以「运行时」那一层只能先定接口规则，不定实现。

2026-11-03 作者定了两个目标：

- **扩展点开放**。
- **不存在黑箱**：软件这边的开放不留暗处，谁加了什么、谁改了哪里都看得见；同时允许扩展对软件和别的扩展注入（像 Minecraft 的 mixin），自定义程度越高越好。

现状：

- 已经有插件的雏形。[desk/outline](../../../desk/outline/host.go)、`desk/phone`、`desk/exportdialog`（后两个现在是扩展 `ext/phone`、`ext/export`）各经自己的 `Host` 接口取宿主能力，由 [desk/host.go](../../../desk/host.go) 的 `appHost` 实现；命令只有 [desk/commands.go](../../../desk/commands.go) 一张表；AI 工具只有 [discussion/tools.go](../../../discussion/tools.go) 一张表。
- 这些 `Host` 直接交出 `*editor.Editor`、`*book.Book`、`*kit.Palette`、`*ui.Context`。仓库里的 Go 代码这么用没问题；脚本或 wasm 里的代码拿不住这些指针，`mygo vet` 也禁止把 `*ui.Context`、`ui.Element` 留到帧外。
- `desk` 约 2.9 万行，状态集中在 `App`（见[理一遍代码](../../implemented/architecture/2026-10-21-code-reorganization.md)和[desk 状态](../../implemented/architecture/2026-10-22-desk-state.md)）。
- 扩展的数据没地方放：`workspace` 读 jsonl 时遇到不认识的字段直接报错；[prefs](../../../prefs/prefs.go) 是固定字段，[shelf](../../../shelf/shelf.go) 是本机设置，都没给扩展留位置。
- `mygo.Plugin`（mygo 的 `plugin.go`）是「Go 服务 + 网页里的 JS 包」，服务 webview 页面，Inkgo 的原生界面用不上它。

2026-11-03 调研了 VS Code、Forge / NeoForge / Fabric（含 Mod Menu）、Obsidian、JetBrains、cordis（Koishi 的内核），下文标了出处的做法来自这次调研。

## Proposal

分三层。现在做第一层；第二层的数据契约跟着第一层定，先只在仓库里用；第三层等 mygo。宿主给扩展的 API 另写一篇：[扩展 API](2026-11-03-extension-api.md)。

### 核心和扩展

- **核心**只有四样：编辑器、目录（章节树）、存储（`workspace`）、扩展宿主。核心不能关，也不能被替换。
- **扩展宿主**是核心里管扩展的那部分，相当于 Forge 或 Fabric Loader 本身：登记表、依赖和加载顺序、开关和连带开关、每个扩展的状态和出错记录、设置的外壳（对话框、导航、照声明画扩展的设置）、「扩展」页和扩展详情页。宿主本身不开注入点：它记账，谁加了什么、谁注入了哪里都由它记、由它显示；能注入它，扩展就能抹掉自己的痕迹。Fabric 也一样，mod 改得了游戏，改不了 Loader。
- 其余都是扩展，包括设定、大纲、AI。作者 2026-11-03 定：它们对外宣传是软件的核心功能，架构上独立于软件。它们随软件带、默认开。
- 扩展分两种（像 Forge 的前置 mod）：
  - **功能性扩展**：有界面，作者开关它。
  - **前置扩展**：只定约定、提供基础能力，自己没有界面，给别的扩展用。现在有三个：
    - **context**：书的资料（设定条目、章纲、卷纲，以后的伏笔、批注……）长什么样，到哪里登记、从哪里取。设定、大纲往里供；讨论、检查、起草、名字补全、MCP 从里面取。提供的和用的只依赖 context，彼此不认识。
    - **marks**：正文上的标记（高亮、边注、点了跳过去）。编辑器只认 marks，伏笔、批注、检查往里放标记。
    - **AI**：只管服务和模型调用，并开一个「AI 工具」的扩展点，别的扩展往里登记工具（作者 2026-11-03 定）。用到 AI 的界面都在依赖它的功能性扩展里。

### 依赖和连带开关

- **必需依赖**（Requires）：
  - 打开一个，它依赖的一起打开；
  - 关掉一个，依赖它的一起关；
  - 拨开关之前，那一行先写明会连带开、关哪些；
  - 再打开时，各扩展回到自己原来的开关。
  - 开着的才加载，关着的不加载。页面上全看得见，不偷偷按需加载。前置扩展也列在「扩展」页、也有开关，规则相同。
- **可选依赖**（Optional，作者 2026-11-03 要；JetBrains 的 `optional="true"`、NeoForge 的 `optional`、Fabric 的 `recommends`）：
  - 对方开着就用，没开也照常工作，只是少了靠它的那部分；
  - 不连带：打开一个，不会把它的可选依赖打开；关掉可选依赖，依赖它的不跟着关；
  - 对方开着时，排在对方之后启动；
  - 能取对方的服务（取的时候先问在不在）、往对方的扩展点里放东西、注入对方。对方没开时这些什么也不做，详情页写「X 没开，以下不生效」；
  - 对方中途开、关，用到它的那部分跟着出现、消失，不用重启依赖方。
- 往一个扩展上注入，要把它写进必需依赖或可选依赖。往可有可无的东西上注入，就写成可选依赖（Fabric 的可选 mixin 也是这样）。
- 双方都要用的东西，仍放进 context 这样的前置扩展，让提供的和用的彼此不认识。
- `cmd/inkgo` 用一份显式清单装配：`ext.Use(context.Module, lore.Module, …)`，不用 `init()` 加空白 import 的隐式登记。测试查两件事：没有环、id 不重复。
  - 清单的顺序就是「扩展」页上的顺序，照原型的 `EXTS` 一组一组排。加载顺序宿主自己按依赖算（必需、可选都算，依赖的先，同等的按清单顺序），停的时候倒过来。原来要求清单里被依赖的排在前面，结果总览的顺序跟着加载顺序走，2026-11-05 拆开了。

### 开关：全局和按书

- 全局开关在设置的「扩展」里，存在本机，是默认值。
- 每本书可以盖过它，三种状态：跟随全局（默认）、本书开、本书关。存在书里。
- 平时不写哪一级：开关管本机的所有作品。这部作品单独设了，页头才多一句「本作品里已关闭」。单独设放在页头右上角的「⋯」里：「只在本作品关闭」或「只在本作品打开」，单独设过的是「恢复默认」（VS Code 扩展的 Disable (Workspace)）。作者 2026-11-03 看了三种把范围写出来的方案，说「这样好冗余」，要照 VS Code 的做。
- 连带开关按这本书最终的状态算。换书时最终状态变了的扩展会开或关，所以开、关都要便宜，并有测试。

### 替换和注入

- 凡是经宿主走的调用都能注入：
  - 扩展之间、扩展和核心之间的调用：执行命令、画右栏标签、从 context 取资料、写一种导出格式……
  - 核心声明的点：编辑器处理按键、画正文……
- 注入分四种：
  - before：调用前跑，能改参数；
  - after：调用后跑，能改结果；
  - around：把调用包起来，决定调不调原来的；
  - overwrite：整个换掉。「替换一项贡献」就是 overwrite 它。
- 宿主内部和没经宿主走的 Go 函数不能注入：Go 不能安全地改写任意函数的机器码（见「Alternatives considered」）。
- 前三种可以叠好几层，按顺序排，顺序页面上可见。作者调过的顺序存进设置。
- overwrite 同一处只能有一个（Mixin 的教训：overwrite 最容易冲突）。
  - 两个扩展抢同一处时，两个都不生效，原来的照跑，那一处标冲突，等作者在页面上选。
  - 关掉替换方，原来的自动回来。
- 被注入的那一处列出整条链，比如「导出 docx：A 改了参数 → 原来的导出 → B 改了结果」。被替换的写明「由 X 提供（替换了默认的）」。

### 透明度

- 每个扩展一页详情，全部来自宿主的账：
  - 说明；
  - 需要谁、可选用谁、被谁需要；
  - 加了什么：扩展关着也列得出，见 API 篇的「只记录不生效」；
  - 注入了哪里、哪一种、排第几；
  - 提供和用了哪些服务；
  - 有哪些设置；
  - 数据目录和大小；
  - 状态（关着、启动中、开着、出错）和出错记录。
- 所有 id 带扩展名做前缀（`phone.open`、`lore.entry`），出处一眼看得出；同名启动时就报错，不覆盖（Forge 的注册表、Obsidian 的命令前缀）。
- 两个扩展抢同一个快捷键时，快捷键表标出冲突，写明哪个生效、怎么改（VS Code 的「Show Same Keybindings」）。
- 一个扩展出错只停它自己（连同必需依赖它的），提示条和详情页写明是哪个扩展、在谁的注入里（cordis 的作用域、JetBrains 的报错框）。
- 原型 2026-11-04 照上面做了详情页的下半截和两种冲突，等作者看（我的提议）：
  - 页头和设置下面，按有没有分四段，没有的那段不画：「功能入口」（它在界面上加了什么，按地方说：「右栏的一页：设定」「正文右键菜单里的项」「导出的一项：设定」，状态、排版这些看不见的不列，扩展关着也列）、「介入」（「编辑器处理按键：在它之前」）、「数据」（「本作品的 ext/lore，12.5 KB」「这台电脑上的 ext/phone，0.4 KB」）、「出错记录」（「今天 10:32 · draw：draw failed」，新的在上）。几个扩展合用的设置页（「提醒」）不画这些，进各自的页才看得到。
  - 提供和用了哪些服务、状态（启动中、出错）没单独列：服务是给扩展看的，作者从页头的「需要」「要用它」已经看得出谁连着谁；开没开看页头的勾。等作者看了再定要不要。
  - 替换冲突：「少见的情况」里装上两个假装另装的扩展（竖排导出、古籍版式），都要替换「导出 docx」。两个的页上「介入」那一行写琥珀色的「导出 docx：古籍版式也要替换它，两边都没生效，暂用默认的。」，下面一排单选：默认的、竖排导出、古籍版式。选了的写「替换了默认的」，没选上的写「没生效，用的是竖排导出」。宿主的 `ext/injection.go` 已经照这条规则处理冲突、也留了作者选的那一位，缺的只是这个界面。
  - 快捷键冲突：古籍版式也要 Ctrl+L（讨论的引用在用）。快捷键表那一行下面一句琥珀色的「古籍版式也要这个键，现在「讨论」的生效。不要的那个可在「扩展」里关掉。」随软件带的、先装的生效；软件里还不能改键，所以「怎么改」写的是关掉一个。
  - 现在随软件带的扩展之间没有替换、没有抢键，这两种冲突要等能另装扩展（第二层）才会真出现。

### 设置

- 扩展声明自己的设置：类型、默认值、范围、可选项（每项带说明）、分组、顺序、作用范围（全局、按书、两者都有）。宿主照声明用 `kit` 画，样子和其余设置一致（VS Code 的 `contributes.configuration`、NeoForge 的 `ModConfigSpec`）。
- 复杂的设置，扩展可以用 `kit` 的零件自己画一整页（NeoForge 的 `IConfigScreenFactory`、Obsidian 的 `PluginSettingTab`），作者 2026-11-03 同意。详情页标明「自定义设置页」。
- 设置本身不是扩展（作者 2026-11-03 同意）：
  - 外壳归宿主，不能关、不能替换：对话框、导航、「扩展」页、扩展详情页、照声明画设置的部分。「扩展」页在设置里，设置能关就没处再打开；能替换的话，扩展就能把自己从「扩展」页藏起来。
  - 内容归各扩展，经宿主开的「设置项」「设置页」两个点放进来：AI 那一页归 AI，备份归备份；原来的「提醒与检查」拆开，伏笔提醒归伏笔，检查归检查，同放在「提醒」一页；外观（字号、行距）归核心，因为是编辑器的。
- 导航的排法：
  - 上面是宿主和核心的：外观（语言也在里面）、扩展；
  - 下面是扩展登记的页。登不登记、页名、顺序都由扩展自己声明，作者 2026-11-03 说：「这个可以自由选择是否注册进去，然后注册的顺序是什么，这个应该属于拓展的一部分」。不登记的，设置只在「扩展」里它自己的页；
  - 登记了的页一直在，扩展关着也在：页头的开关能把它再打开。
- 两个扩展登记同一个页名，就合用一页（伏笔和检查同在「提醒」）；每一项是谁加的，详情页里看得到。

### 数据

- 每本书的扩展数据放书里的 `ext/<id>/`，按书的开关和设置放 `ext.json`；本机的放 shelf 旁边的 `ext/<id>/`，各带自己的 schema 版本。`workspace` 给出这块目录（`Store.ExtDir`）。
  - 最初写的是 `.writer/ext/<id>/`，2026-11-04 落地时改了，因为备份跳过 `.writer/`，新书的 `.gitignore` 也忽略它。放在那里，设定、大纲就不进备份、不进 git。
  - 现在 `.writer/` 只放本机的状态和缓存（`desk.json`）。
  - 这是我的提议，作者没有另说。
- 设定、大纲现在的文件也搬进各自的目录。作者 2026-11-03 定：快速开发期不考虑任何向后兼容，已有的书不迁移，测试用的书用 `cmd/sample` 重新生成。

### 正文标记的标记点（2026-11-04 提议，等作者看）

顺序第 4 步要先定编辑器怎么画别的扩展的标记。原型里已经照下面这样做了（`prototype/write.js` 的「正文标记」一节）：

- **经正文标记的**：正文上留着、要跟着正文挪的标记。扩展登记一个来源，给出开着的这一章里每一处的位置（哪一段、哪几个字）、样子、点了去哪、页边的批注。编辑器只画这里给的。现在的来源：
  - 伏笔：埋下、回收的那几个字（必需正文标记）；
  - 检查：和设定对不上的那几个字（必需）；
  - 改稿建议：采纳了的「AI 写的」下划线（可选：正文标记关着时不画，改稿建议照常能用）；
  - 设定：AI 从这一章看出来要改的设定，只在页边有一条批注，正文上不画（可选）。
- **批注**只管把这些批注排在正文旁边（右栏「批注」一页），自己不出标记。
- **不经正文标记、由编辑器直接画的**：选中的字、查到的字、AI 正在提的修改、设定的名字（名字补全）。它们随时算得出来，不用存、不用跟着正文挪，各自的扩展开着才画。这样全书查找、名字补全不用依赖正文标记，和上面的依赖表一致。
- 几处重叠时按登记的先后留先到的：选中、AI 正在提的修改、查到的、伏笔、检查、AI 写的、设定的名字，和改之前一样。
- 正文的右键菜单分三组：剪贴板（编辑器自己的）；续写、改写（改稿建议）、引用（讨论）、加入设定（设定）；伏笔的几项。扩展关着时它的几项不在，一组空了连同分隔线不画。
- 扩展关掉时，它在正文上的标记、页边的批注、右键菜单里的项、待处理里的条目一起消失；再打开都回来。正文标记关掉时伏笔、批注、检查跟着停下（走查 `the marks on the prose go with what puts them there`）。

2026-11-04 问了作者两处：
- 上面「经 / 不经正文标记」的分法（另一种是正文上画的一切都经正文标记）：作者「同意」这样分。

### 翻译表

### 第二层：公开接口

给将来的外部插件用的数据契约：只交出 ID、普通数据和对界面的描述，宿主用 `kit` 画；不交出 Go 指针或帧内对象。这条规则不依赖 mygo 选哪种脚本语言：每帧调一次脚本太贵，脚本也拿不住帧内对象，剩下的路就是返回描述、由宿主来画。注入、替换、设置、依赖在这一层用同一套规矩，只是参数换成普通数据。

### 第三层：运行时

一个适配层，把第二层接到 mygo 将来的脚本方案上。mygo 迟迟不出时的候选：wazero 或 Extism（纯 Go、有沙箱、多语言）、goja（JS）。外部插件从一开始就在清单里声明权限（读哪些数据、能否联网）和要求的宿主 API 版本（VS Code 的 `engines.vscode`），由宿主强制执行。

## Alternatives considered

- **Go 标准库的 `plugin` 包** — 最强的理由是插件就是 Go，能直接拿宿主的类型。没选：只支持 Linux、FreeBSD、macOS，关掉 cgo 时直接用 stub 返回 not implemented（`$GOROOT/src/plugin/plugin_stubs.go` 的构建条件是 `!cgo`）；宿主和插件要用同一工具链、同一份依赖构建。Inkgo 是 `CGO_ENABLED=0`，还要上 Windows。
- **`init()` 加空白 import 的隐式登记（Caddy、Telegraf 的做法）** — 最强的理由是加模块只动模块自己。没选：顺序藏在 import 里，测试没法只装一部分；模块不多，一份显式清单更好读。
- **HashiCorp go-plugin（子进程加 gRPC）** — 最强的理由是进程隔离，插件用什么语言都行。没选做界面插件：每次调用都跨进程，画界面撑不住。以后做「后台跑、不画界面」的插件（导入、联网查证）可以再看。
- **Yaegi（Traefik 的 Go 解释器）** — 最强的理由是插件作者写的还是 Go。没选：只能写 Go，解释执行慢，解释的代码不经过 `mygo vet`。
- **现在就选定 wasm 或 goja，先做外部插件** — 最强的理由是早一点让外部开发者用上。没选：mygo 说过要出自己的方案，现在选定，以后多半要换；第一层、第二层不管选哪个都得先做。
- **拿 MCP 当插件机制** — 最强的理由是 AI 工具已经都会说 MCP。没选：MCP 管的是 AI 能调用什么（工具、资源、提示词），不管界面；Zed 用它接 context server，也正打算弃用这条扩展路线。
- **扩展只许往预留的位置放东西，不许改别人的界面和行为** — 最强的理由是 [DESIGN.md](../../../DESIGN.md) 的一致性好守，VS Code 也不给扩展碰 DOM。没选：作者 2026-11-03 要高自定义，允许注入和替换。一致性改由两条守：随软件带的扩展照 DESIGN.md 写、照样走检查；装了别人改界面的扩展是作者自己的选择，详情页写明它改了哪里。
- **设定、大纲、快照、回收站、查找算核心** — 最强的理由是设定、大纲是 AI 上下文和检查的数据来源，快照、回收站防丢稿，拆出去要多绕一层。没选：作者 2026-11-03 定架构上独立于软件；数据来源的问题由 context 解决。
- **只有必需依赖，双方都要的东西全放进前置扩展** — 最强的理由是关系只有一种，依赖不会越连越多。没选：作者 2026-11-03 要可选依赖；「有它更好、没它也行」的功能（导出带上大纲、设定）硬放进前置扩展会多出一堆只为接线的扩展。
- **AI 做成一个功能性扩展，连用量记录一起** — 最强的理由是「关闭 AI」一个开关就够。没选：作者 2026-11-03 定 AI 是前置扩展，只管服务、模型调用和工具登记；用量记录单独一个。关闭 AI 仍是一个开关：关掉 AI，依赖它的连带关掉。
- **前置扩展按需加载，不给开关（Mod Menu 默认藏起 Library）** — 最强的理由是作者不用管它们。没选：作者 2026-11-03 定页面上不要黑箱。
- **服务一出现就自动启用依赖方（cordis 的 `inject`）** — 最强的理由是不用作者动手。没选：开关要看得见，改成显式开关加连带开关，效果相同。
- **设定、大纲的文件留在原处，只把代码挪进扩展** — 最强的理由是已有的书不用迁移。没选：作者 2026-11-03 定快速开发期不考虑向后兼容。
- **只有全局开关** — 最强的理由是简单，「扩展」页只有一层。没选：作者要按书关掉用不着的功能（VS Code 能按工作区停用扩展）。

## Acceptance criteria

- 手机预览、导出、备份迁到 `ext/` 后行为、截图不变，`npm run verify` 全绿。
- 三个扩展全经登记表接入，`desk` 里不再有它们的具体名字（装配清单除外）。
- 每条规矩有一个用假扩展的测试（细目在 API 篇）：连带开关；关着也列得出加了什么；id 重名报错；overwrite 冲突时原来的照跑；关掉之后，它在宿主账上的东西一条不剩。
- 停用一个扩展，它的命令、菜单项、标签页、注入都消失，再启用都回来，不用重启。
- 依赖边界测试覆盖 `ext/` 下每个包：import 了谁的公开包，谁就必须在必需依赖或可选依赖里。
- 原型里「扩展」页、详情页、重排后的设置作者看过。

## Risks

- 登记表先按三个简单扩展设计，到伏笔、检查这类要碰正文的功能时可能不够用。所以先迁三个，再定 marks 和编辑器的标记点。
- `App` 的状态没理清时拆扩展，会把一大块状态整个搬进服务，接口变宽。要和[项目架构审查](2026-10-27-maintainable-project-review.md)里「整理 App 的状态归属」一起排。
- 每帧都跑的注入（画、按键）会拖慢帧，接到现有的帧耗时检查上，见 API 篇。
- 画界面的注入半路出错时，能不能只停那一个扩展而不弄坏这一帧，要先查 mygo（待核实）。
- 允许注入以后，界面的一致性靠随软件带的扩展自觉守、靠作者自己选，不再由结构保证。
- mygo 的脚本方案若要求宿主接口长得不一样（比如是每帧回调），第二层要改。所以第二层先只在仓库里用，不对外承诺。
