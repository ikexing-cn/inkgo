# Agent Note: 以"讨论 + 逐条取舍"为核心的写作 harness

Status: proposed

## Problem

作者常常从"一头雾水、只有一个念头"开始。和 AI 来回聊能冒出很多思路，但现有聊天工具有三个问题：好坏掺在一整条回复里，只能整条接受或忽略；放弃过的方向会被换个说法再提回来；聊了几百轮后，"到底定了什么"埋在对话历史里，模型也装不下。

目标场景：作者和 AI 慢慢讨论，AI 给出思路，作者觉得好就保留，觉得不行就放弃、之后不再提及。产品围绕这个场景设计，本质上是写作领域的 harness：AI 只负责回答和记账，取舍永远由人做。

"思路是基本单位""思路池是唯一依据""从思路到设定"三节的方向已由[设定文档与后台记账](../../implemented/feature/2026-10-08-setting-document-and-background-bookkeeper.md)取代：作者不再逐条取舍，后台把讨论整理成按分类的设定文档。其余部分仍是待做的方向。

2026-10-14 起 AI 可以整个关掉（[可以整个关掉 AI](../../implemented/feature/2026-10-14-disable-ai.md)）：讨论不再是写作软件唯一的中心，关着 AI 时编辑器要能单独用。这一篇的定位照此读。

失败条件：作者变成只会点"继续"的审核员；放弃的思路绕回来；AI 说出和已定设定矛盾的话；稿件或 key 在作者不知情时外泄。

## Proposal

### 思路（Idea）是基本单位

- 每轮回复后，用"记账模型"把双方发言拆成小条思路；拆错时作者可以从原文自己划出一条。每条思路都链接回原文位置。
- 作者自己说的话也拆，标"来源：人"，在卡片列表里排在前面；同样要作者点一下才算数，防止把"要不……捕快？"误读成定论。
- 状态：`未处理`（还没看）→ `保留` / `待定`（看过、没想好）/ `放弃`（可附一句理由）→ `已采用`（已整理成设定）。另有 `被取代`（被细化或合并后的新条目替代）。
- 状态可以随时改，每次改动都追加一条历史（时间、从哪个状态到哪个、理由）。`已采用`的思路要先撤回对应设定才能改。从放弃列表捞回的思路回到`待定`。
- 每条思路有且只有一个主分类，由记账模型自动打，作者可以改。跨类的思路按落点归类，比如"沈砚和师父反目"归"关系"。
- 分类列表在新建作品时从体裁模板复制进 `work.yaml`，之后可以自由增删改。记账模型只能从列表里选，拿不准选"其他"，不得发明新分类。删掉一个分类时，它下面的思路归入"其他"。
- 每个分类注明落点，整理时据此决定往哪里放：

  | 分类 | 落点 |
  |---|---|
  | 人物、关系、地点、组织、物品 | 设定库 |
  | 规则（魔法、科技、社会制度） | 设定库·世界观 |
  | 情节 | 大纲 |
  | 主题 | 作品说明 |
  | 风格（语气、视角、禁用词） | 风格指南 |
  | 其他 | 不整理，只留在思路池 |

  体裁追加：网文加"力量体系"（境界、金手指）；出版小说加"叙事结构"（视角、时间线）；剧本加"场景"；非虚构加"论点"和"资料"（与`事实 · 未核实`联动）。
- 现实世界的事实单独标为`事实 · 未核实`，和虚构思路分开放；作者手动标为已核实并写上来源后才去掉标记。

### 思路池是唯一依据

- AI 后续讨论依据思路池，不依据对话历史；随时可以开新对话，从思路池接着聊。对话只是过程记录。
- 每次请求的上下文分层组装：
  - 当前话题的`保留`、`待定`思路和未解决的冲突，全部给；
  - 全局`保留`思路按相关度挑选；
  - `放弃`思路只给一句话摘要和理由，用于避让；
  - 和当前话题相关的已定设定压成一句话，作为不可讨论、只能遵守的约束；
  - 当前对话最近几轮原文，保证话题接得上。
- `未处理`和`已采用`的思路不作为讨论对象。
- 每条回复都能点开"这次 AI 看到了哪些思路"。

### AI 只回答、只记账，不主动出内容

- 出内容（新点子、反问、提议细化或合并）只在作者要求时发生。
- 记账始终自动进行，它不产生新想法：
  - 拆分思路；
  - 打分类标签；
  - 保留时检查冲突；
  - 新思路和已放弃思路相近时，明确标出"和某条相近，区别在于……"。
- 保留的思路可以互相矛盾，两条都标`冲突`，思路池常驻显示"还有 N 处冲突未解决"。带未解决冲突的思路不能整理成设定。
- 作者点"让 AI 帮我合并/细化"时，AI 生成新条目作为提议，新条目记住来自哪几条，采纳后旧条目标为`被取代`。作者也可以直接改条目。

### 话题

- 每部作品有一个总讨论。作者可以在任意讨论里新建话题，也可以把某几轮对话"移到新话题"。话题可以挂到设定条目或章节上，可以嵌套，界面上默认展开两层。
- 话题里保留的思路全局可见；话题里放弃的思路只对本话题及其子话题生效，可以手动"升为全局"。

### 从思路到设定

在思路池里选几条已保留、没有冲突的思路，点"整理成设定"。AI 起草设定条目，起草结果作为提议。采纳后设定条目链接回来源思路，来源思路转为`已采用`，之后不再出现在讨论里。

### 交互

每条回复下面列出思路卡片，每张卡片有留、弃、待定三个按钮，键盘用 1/2/3 处理，Tab 跳过。放弃时可以顺手写一句理由，回车跳过。卡片可以展开原文。第一版只做独立的讨论界面；写正文时的讨论侧栏、选中正文拿去讨论，后来作为路线第 6 步落地。

### 存储

- 一部作品是一个文件夹，以文件为准：
  - 正文每章一个文本文件；
  - 每条思路、每条设定各一个小文件，状态历史写在文件里；
  - 每次会话一个对话记录文件。
- 文件夹可以直接用 git 管理。
- 另建一个 SQLite 做索引，用于搜索、相近度比对和统计；索引可以删掉重建。M1 不建索引，见[存储去掉索引](../../implemented/architecture/2026-10-08-m1-storage-without-index.md)；M2 需要检索时再引入。

目录结构：

```
<作品>/
  work.yaml                   # 名称、体裁模板、schema 版本、各用途用哪个模型（不放 key）
  ideas/<id>.md               # 一条思路一个文件
  settings/<分类>/<id>.md     # 一条设定一个文件
  topics/<id>.yaml            # 话题：名称、父话题、挂在哪个设定或章节上
  sessions/<id>.jsonl         # 一次对话一个文件，只追加不修改
  chapters/                   # 目录照搬章节树，见正文页笔记
    .order                    # 每个文件夹一个：子节点的顺序、ID 和原标题
    <标题>.txt                # 正文，一行一段的纯文本
    <标题>.outline.txt        # 章纲或卷纲
    <标题>.marks.json         # 标记：位置加原文片段
  history/<节点ID>/           # 正文快照
  trash/<节点ID>/             # 回收站
  .writer/                    # 写进 .gitignore
    index.sqlite              # M2 起使用；可删，重扫文件重建
    embeddings/<模型>/<文本hash>.bin   # M2 起使用；不随索引删除
```

- **思路和设定**：Markdown 正文加 YAML 头信息，正文就是内容本身。头信息字段：
  - `id`、`status`、`category`；
  - `source`：`ai` 或 `human`；
  - `fact`：是否现实事实，为 true 时还有 `verified` 和来源；
  - `topic`；
  - `origin`：`{session, message, span}`，指回对话原文；
  - `conflicts`、`supersedes`；
  - `history`：每条记录有 `at`、`from`、`to`，可选 `reason`。
- **对话**：JSONL，每行一个事件（用户发言、AI 回复等），每条消息有稳定 ID。AI 回复那一行记下这次请求实际发出的上下文条目 ID，"AI 看到了哪些思路"从这里读。只追加不修改，所以 `origin` 的字符范围永远有效；崩溃最多丢最后一行。
- **ID**：`yyyymmdd-hhmm-xxxx`，时间加 4 位随机十六进制。文件名只用 ID 不带标题，改了内容引用也不断。章节同样用 ID 命名，标题和顺序只在头信息与 `order.yaml` 里。
- **章节标记**：正文保持纯文本，标记存在同名的 `.marks.yaml` 里。每条标记记 `kind`、`id`、`at`（rune 范围），以及 `quote`（被标记的原文）和 `prefix`/`suffix`（前后约十来个字）。打开章节时先按 `at` 核对：原文对不上，就用 quote 加前后文在全文里重新定位；仍然找不到，标为 `Orphaned` 让作者处理。这是 W3C Web Annotation TextQuoteSelector 的思路，用别的编辑器改过正文或 git 合并后，标记也不会丢。
- **写入**：先写临时文件再改名，避免留下半截文件。每个文件都带 schema 版本，格式变了能自动迁移。
- **依赖**：YAML 用 `go.yaml.in/yaml/v3`，按结构体严格解析，拼错的字段直接报错。SQLite 用 `modernc.org/sqlite`，纯 Go，`CGO_ENABLED=0` 照样能编译，M2 起引入；届时再决定全量重扫还是用修改时间加内容 hash 判断是否过期。

### 模型接入（BYOK，参照 DeepSeek Harness 的模型设置）

- 两种接入方式：
  - 预置提供商：DeepSeek、Kimi（Moonshot）、OpenAI、Anthropic。填 API key，key 留空就读环境变量；"自定义设置"里可以改 API 地址等。
  - 自定义模型 API：用于中转站、自己部署的服务、Ollama。要填 Provider ID（小写标识）、显示名称、API 地址，协议选 OpenAI Chat Completions、OpenAI Responses 或 Anthropic Messages；模型目录可以手动添加，也可以"获取可用模型"拉取，目录外的模型 ID 照样能直接发请求。
- 有"打开配置文件"按钮，配置可以手改。
- 提供商配置放在用户目录的全局配置里，key 存进系统钥匙串。作品文件夹只记"哪个用途用哪个提供商的哪个模型"，不放 key。打开别人的作品时，如果本机没有对应的提供商，提示作者重新选。
- 按用途选模型，第一版分两种：`讨论`和`记账`。`记账`不单独指定时沿用`讨论`的模型。

### 分阶段

1. **M1**：
   - 作品文件夹和存储格式；
   - 模型配置；
   - 总讨论界面；
   - 思路拆分和卡片标记；
   - 思路池视图：各种状态、冲突、放弃列表、"AI 看到了什么"。
   - 上下文组装：不做检索，按分层规则全部发送，超出 token 预算时按"当前话题优先、越新越优先"截断，截掉的条目在"AI 看到了什么"里列出。
   - 相近检测：由记账模型对照放弃清单的一句话摘要来判断。
   - 预留 embedding 接口和缓存目录格式，但不接入。
2. **M2**：embedding。2026-10-15 改为给讨论模型搜、读全书的工具，不做 embedding，见 [AI 基建](../../implemented/architecture/2026-10-15-ai-infrastructure.md)；下面几条是原来的计划。
   - 新增第三种用途`向量`，单独配置提供商。DeepSeek 和 Anthropic 官方 API 据了解不提供 embedding，实现前要核实；Kimi 尚未确认。
   - 保留思路和已定设定按相关度召回前 K 条，再截断到 token 预算。
   - 相近检测分两步：先用向量找出最像的几条已放弃思路，再交给记账模型判断。
   - 向量缓存按"模型 + 文本 hash"存，内容不变不重复调用。embedding 模型按作品固定，换模型就全部重新生成。
   - 没配 embedding 时，退回 SQLite FTS5 trigram 关键词检索。
   - 默认推荐哪种 embedding、K 和阈值取多少，到 M2 时用 M1 攒下的真实数据再定。
3. 话题。
4. 整理成设定。
5. 接入正文编辑器（现有的 `editor/`）。
6. 写作时的讨论侧栏。已落地，见[实现笔记](../../implemented/feature/2026-10-08-discussion-beside-the-prose.md)。
7. 联网核实事实：给 AI 加搜索工具，事实附来源链接，新增"核实"这种用途。

### M1 实现边界与施工约定

M1 已随代码落地，具体契约、取舍与验证见[实现笔记](../../implemented/feature/2026-10-07-m1-discussion.md)。本篇仍为 proposed，承载后续 embedding、话题、设定和正文集成；M1 不包含 AI 合并/细化操作。

- M1 使用独立的 `workspace`（文件与可重建索引）、`model`（全局配置、凭据、三种协议）、`discussion`（上下文、记账、状态操作）、`desk`（原生界面）包，入口保留现有编辑器演示并增加讨论模式。
- 网络请求在后台执行，通过结果通道回到界面线程；同一作品同一时刻只允许一个修改操作，避免回复和卡片操作覆盖文件。请求可取消，失败后保留已落盘的对话，记账可重试且不重复生成卡片。
- 记账输出采用严格 JSON 契约，来源必须是本轮消息中的原文片段；无效来源、未知 ID 和非法状态不得写入。模型只提供分类、相近与冲突建议，不替作者决定留弃。
- M1 仅总话题；话题树、整理设定和正文章节读写仍在后续阶段。存储预留相关字段与目录，不把后续阶段标为已实现。
- 上下文预算使用保守的 UTF-8 字节估计（至少覆盖常见 tokenizer），预留回答空间；预算连系统规则与当前发言都容不下时明确报错。截断记录与实际发送同步保存。
- 原有编辑器笔记与本篇部分重叠：原生 UI 与纯 Go 约束沿用[编辑器决策](../../implemented/architecture/2026-10-07-pure-go-native-editor.md)，编辑器实现不被替换；流程笔记只约束门禁，无业务重叠。

### 开放问题

- M2：默认 embedding 模型（本地 Ollama + bge-m3，还是 OpenAI），召回数 K，相近阈值。M2 已改为工具式检索，这一条不再需要定，见 [AI 基建](../../implemented/architecture/2026-10-15-ai-infrastructure.md)。
- 章节版本快照的格式，到接入编辑器时再定；在那之前先用 git。已在[正文页](../../implemented/feature/2026-10-08-writing-page-and-chapters.md)中落地，该篇是路线第 5 步的第一期；第二期见[AI 辅助写作](../../implemented/feature/2026-10-08-ai-assisted-writing.md)，也已落地。

## Alternatives considered

- **以完整对话历史为准** — 最自然，不用额外设计数据结构，任何聊天工具都能这么做。但几百轮后模型装不下，还越聊越乱；"放弃了不再提"在长对话里做不到，因为放弃的内容仍然留在历史里。
- **整条回复作为留弃单位** — 交互最简单，没有拆分出错的风险。但一条回复里常常有好有坏，整条取舍会逼作者和稀泥。
- **只有留和弃两种状态** — 每次判断最快，思路池最干净。但构思初期很多思路当时判断不了，只能二选一，要么什么都留，要么错杀。
- **放弃即删除** — 实现最简单，"不再提及"天然成立。但删除后 AI 无从知道哪些方向被否过，会换个说法提回来；作者也没法捞回。
- **AI 主动发散或收敛（两种模式）** — 能帮作者快速打开思路。作者明确否决了：要靠人自己的发散思维，AI 主动出内容会让人变成只会点"继续"的审核员。
- **保留即成为正式设定** — 少一步确认。但讨论中保留的只是"方向不错"，常常互相打架；设定库要作为写正文和一致性检查的依据，标准必须更严。
- **已定设定完全不给 AI** — 上下文最省。但 AI 会说出和设定矛盾的话，作者得在讨论里反复纠正。
- **所有思路放在一个 JSON/JSONL 文件** — 文件少，读取快。但 git diff 要在一大坨里找改动，两台机器同时改必然冲突，手修困难。
- **头信息用 TOML** — 语法更严格，坑比 YAML 少。但作为 Markdown 头信息，YAML 是事实标准，其他工具基本只认 YAML；YAML 的坑用严格解析就能规避。
- **文件名带标题摘要（`<id>-卧底.md`）** — 在文件夹里一眼能认出是哪条。但内容改了以后文件名就和内容对不上，改名又会打断引用。
- **M1 就接入 embedding 召回** — 一开始就不怕上下文撑爆。但 M1 阶段思路只有几十条，全部发送也装得下；而且没有真实数据时，K 和阈值只能拍脑袋定。所以先把接口和缓存格式定好，M2 再接入。
- **标记直接写进正文（`{伏笔:…}`）** — 最直观，外部修改也不会丢标记。但正文被语法污染，导出前要清理，在其他编辑器里也难读；AI 采纳标记往往每段都有，正文会变得很难看。
- **标记文件只记位置** — 最简单。但用别的编辑器改一次、或者 git 合并一次，位置就全乱了。
- **一条思路可以有多个分类** — 更贴合实际，很多思路同时涉及人物和情节。但整理成设定时需要唯一的落点，多分类会让落点不明确。
- **章节文件名用标题（`第三章-雨夜.md`）** — 在其他工具里一眼能认出是哪章。但改标题或调整顺序都要改名，会打断引用。
- **单一 SQLite 存储** — 查询方便，一个文件好迁移。但没法用 git 看 diff，文件坏了不好手修，作者带走数据也不方便。
- **只支持云端或只支持本地模型** — 实现面更小。但现在主流服务都有 OpenAI 或 Anthropic 兼容协议，同时支持两者成本很低；而作者对未公开的稿子发给第三方普遍很在意。
- **预置一长串提供商** — 开箱即用。但要先自己用，维护用不上的配置不划算；其他服务走自定义 API 就够了。

## Acceptance criteria

M1 完成时可以观察到：

- 从空文件夹新建作品，在总讨论里和配置好的模型来回聊；每轮下方出现拆好的思路卡片，用 1/2/3 标记后文件夹里出现对应的思路文件，状态历史正确。
- 关掉软件再打开、或开一个新对话，AI 接着聊时依据的是思路池；放弃的思路不会原样或换个说法回来，相近的新思路一定带"和某条相近"标注。
- 保留两条矛盾的思路后，思路池显示未解决冲突数。
- "AI 看到了哪些思路"能列出这次请求实际发出的上下文条目。
- 预置提供商和自定义 API 都能配置成功，三种协议都能对话；作品文件夹里搜不到任何 key。
- 删除 `.writer/` 后重新打开作品，数据不丢（M1 不建索引）。
- 思路池超出 token 预算时，按规则截断，"AI 看到了什么"列出被截掉的条目。
- 手改一条思路文件的头信息（比如拼错一个字段）后打开作品，会报出具体的文件和字段，不会静默忽略。
- 门禁：`go vet ./...`、`go test ./...`、`npm run verify-notes` 通过；拆分、上下文组装、状态流转和存储读写都有不依赖真实模型的单元测试（用假的模型应答）。

## Risks

- **拆分质量决定一切**：记账模型拆得太碎、太粗，或者误读作者的话，标记就会变成负担。缓解：作者能手动划，能合并、改条目；拆分的提示词和样例纳入测试。
- **"不再提及"无法绝对保证**：模型可能无视避让清单。缓解：用相近检测兜底标注；"AI 看到了什么"便于排查漏送。这个做法只能减少重复，不能百分之百杜绝。
- **标记疲劳**：每轮都有卡片要处理，作者可能干脆不标。`未处理`不进思路池，不会污染依据，但思路会丢；要观察实际使用中未处理占多少。
- **上下文挑选出错**：M1 截断时，或者 M2 召回选错时，AI 会说出和没送进去的保留思路或设定矛盾的话。M1 阶段思路池涨得快的话，截断会提前出现；如果"AI 看到了什么"里经常有被截掉的条目，就提前做 M2。
- **embedding 重建成本**：向量缓存不进 git。换机器或换 embedding 模型时，要重新调用 API 生成，会花钱也要花时间。
- **稿件外泄**：用云端模型时，讨论内容会发给第三方；配置界面要明确标出提供商是本地还是云端。
- **mygo 还不成熟**：讨论界面需要的列表、卡片、滚动是否够用尚未验证；不够用就得自己画，工作量会变大。
- **回滚**：后续阶段仍是提议；已落地 M1 的格式与实现边界见实现笔记。前提变化时保留已有数据，不把不兼容版本静默读成当前格式。
