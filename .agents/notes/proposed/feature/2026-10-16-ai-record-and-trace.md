# Agent Note: 每次请求记一行「AI 记录」，另有内部用的完整请求

Status: proposed

## Problem

2026-10-16 作者说：「摘要和检查的形式我在思考，感觉现在很浪费token而且没办法直观看到用途。」又说：「这个会不会也有点黑盒，给个预览AI到底在干什么的入口会好点（可以内部测试的看情况）」。

现在作者能看到的：

- 讨论回复下面的「AI 参考内容」和这一轮的 token 数（DESIGN.md「模型看到的，作者也看得到」）。
- 起草、改写只有采纳了才在快照里留一份 `AIRecord`；没采纳的什么也不留。
- 续写、摘要、检查发了什么、花了多少，界面上哪里都没有。
- `usage.json` 按「服务商/模型」各记一行累计数（[AI 写的字等作者采纳，作品记下用量](../../implemented/feature/2026-10-15-ai-text-waits-and-usage-is-kept.md)），看得出总共花了多少，看不出花在哪个功能、哪一章。
- 调提示词的人只能自己在代码里打印，没有现成的办法看一次请求的全文。

## Proposal

### AI 记录

- **每次向模型发请求都记一行**：完成的、失败的、作者取消的、被截断或被过滤的都记。一行有：
  - 时间、用时；
  - 功能：讨论、起草、改写、续写、检查；
  - 哪一章（章节 ID，显示时换成章名；章已删除的写「已删除的章节」），讨论的还有哪段讨论；
  - 模型和思考程度；
  - 发出去的各部分各约多少 token（就是现在 `workspace.Sent` 的 `Parts`）；
  - 服务商算的实际用量：输入、缓存命中、缓存写入、输出、推理；
  - 按内置价格估算的花费和币种；
  - 结果：完成，或失败的原因、已取消、已截断。
- **不存正文、设定、讨论的文字**：这些在作品里本来就有；记录只说发了哪几部分、各多大。
- **讨论里的请求按讨论的来处算功能**：从起草入口开的讨论（见[起草和改写交给讨论](2026-10-16-writing-through-the-talk.md)）里每次请求都算「起草」，改写的算「改写」，其余算「讨论」。压缩讨论的那次请求也算它所在讨论的功能。
- **存在作品里，一直留着**：作品根目录一个只追加的 `ai-log.jsonl`，和 `work.yaml` 并排，随作品备份。读写走 `workspace/jsonl.go`，最后一行写了一半时丢掉那一行。只能看，没有删除和清零。
- **`usage.json` 不再写**：累计数从记录算。记录文件还没有、`usage.json` 在时，打开作品时转一次：每个模型一行「此前的用量」，只有 token 和花费，没有时间、功能、章。转完 `usage.json` 留在原处，不再读。
- **记账还是只有一处**：`ai.open` 给客户端包的 `counted` 原来记用量，改成记这一行。哪个功能、哪一章、哪段讨论，由发请求的地方放进 `context`，`counted` 取出来写上。

### 设置里看

- 设置「AI」的「本作品用量」展开成两层：
  - 按功能各一行：请求数、token、估算花费，和现在一样注明「按内置价格估算，以服务商账单为准。」；
  - 「查看全部记录」：按时间倒序一行一次请求，能按功能筛。点开一行看各部分的 token 和实际用量。
- AI 关着时整个不显示，记录留着，和讨论、检查结果一样（DESIGN.md「AI 可以整个关掉」）。
- 具体排法先在原型里做出来给作者看。

### 讨论回复写上钱

回复下面那一行，「· N token」后面加估算花费：「· 42K token · 约 $0.08」。token 数照 DESIGN.md 文案那一条按 K、M 写；表里没有价格的模型不写花费。这是这一轮所有请求的和，和 token 数一样。

不在发请求之前报价：讨论带工具，查几次、写多长事先不知道，报出来的数不准；起草对话框改成说清会预先带上哪些内容、约多少 token（见[起草和改写交给讨论](2026-10-16-writing-through-the-talk.md)）。

### 内部用的完整请求：`-trace <文件夹>`

- `cmd/poc` 加一个参数 `-trace <文件夹>`。带了它，每次请求在那个文件夹里写一个文件：完整的系统提示词、消息、工具调用和工具结果、模型的原始回复、用量。文件名是时间加功能。
- 只写进给的文件夹，从不写进作品；界面上没有入口，不进设置。
- 也挂在 `counted` 那一层，和 AI 记录同一处，不会漏掉哪种请求。

## Alternatives considered

- **在作品里存每次请求的全文** — 最强的理由是作者能看到 AI 到底读了什么，不用再从代码推。没有用：一次请求几万字，作品文件夹涨得很快，备份也跟着大；正文、设定、讨论本来都在作品里，记各部分的大小就够作者判断钱花在哪。要看全文的是调提示词的人，用 `-trace`。这一条和[每次请求由同一个拼装器装](../../implemented/architecture/2026-10-15-one-budget-for-every-request.md)里否掉的是同一件事。
- **每次用 AI 之前先报价，作者点了才发** — 最强的理由是钱花之前作者就知道。没有用：讨论查几次、回多长事先不知道，报的数会差很远，作者按它做决定反而上当；每个功能都多一步确认也烦。改成事后每一笔都看得到，起草前说清预先带上多少。
- **`usage.json` 留着，另加记录** — 不动已经测过的累计和校验。没有用：同一件事两处记，迟早对不上；累计数从记录算只要一次加总。
- **记录放在 `.writer/` 里** — 那是本机缓存，不进备份，坏了不心疼。没有用：作者要的是这部作品一直以来花了多少、花在哪，换台电脑也该在。
- **`-trace` 做成设置里的开关** — 作者自己也能看全文。没有用：全文里有整章正文和讨论，写到哪个文件夹、留多久都得另外交代；作者要的「AI 在干什么」由 AI 记录和「AI 参考内容」回答。以后作者真要看全文，再在原型里做。

## Acceptance criteria

- 讨论、起草、改写、续写、检查各发一次请求（有一次失败、一次取消），`ai-log.jsonl` 里各有一行，字段齐，没有正文、设定、讨论的文字。
- 从起草入口开的讨论里查书、提议，每次请求都记成「起草」。
- 只有 `usage.json` 的作品打开后，「本作品用量」的总数和原来一样；`usage.json` 没被改。
- 设置「AI」能按功能看花费、能打开全部记录；AI 关着时看不到，打开 AI 后还在。
- 讨论回复下面写着这一轮的估算花费；表里没有价格的模型不写。
- `-trace` 给的文件夹里每次请求一个文件，内容是完整请求和回复；作品文件夹里没有多出任何东西。
- 原型先做，`npm run verify-prototype` 走一遍；`npm run verify` 全过。

## Risks

- 记录只追加、不清理，一部写了几年的作品会有几万行。每行几百字节，十万行几十 MB；打开设置时要读全文件算总数，嫌慢再加按月的累计。
- `context` 里带功能和章，漏放的地方会记成空。测试里每种功能都要走一遍。
- `-trace` 的文件里有完整正文和 key 以外的全部请求内容，只该在本机调试时用；它不读 key，但服务商返回的报错原样写进去。
