# Agent Note: 讨论查阅到头时不逼模型作答

Status: proposed

## Problem

[讨论用工具查全书](../../implemented/feature/2026-10-15-talk-looks-up-and-notes-the-setting.md)的「一次回复」定了两处收尾，都会在资料不够的时候逼模型作答：

- **10 步上限**（`ext/talk/engine/engine.go` 的 `maxSteps`）：第 9 步的结果后面加一句「已达到本次查阅的上限，不能再查了，请用已经查到的内容回答」；第 10 步仍带工具，但发 `tool_choice: none`，模型只能回答。
- **放不下**：查到的内容超出剩下的空间时，这一个结果在请求里整条换成「这次查到的内容太多，放不下了；不能再查了，请用已经查到的内容回答」（`fullNote`），下一步也不许再调工具。模型连这次查到的东西都看不见，就得作答。

作者 2026-11-06 看了以后说：「1 的设计感觉不好，你看看 codex dsh pis 怎么做的，这个会导致模型没有足够的上下文乱编造内容」。看完调研后说：「第一条记录笔记，后面再改」。

## Proposal

### 三家怎么做

Claude 让 haiku 读了三家的源码（2026-11-06），关键数字 Claude 用 gh 核对过：

| | Codex CLI（`openai/codex`） | pi（`badlogic/pi-mono`） | DeepSeek Harness（`deepseek-ai/deepseek-harness`） |
|---|---|---|---|
| 步数上限 | 没有，模型不再调工具就结束（`codex-rs/core/src/session/turn.rs`） | 没有（`packages/agent/src/agent-loop.ts`） | 没有（`packages/core/agent-loop/src/agent.ts`） |
| 最后一步禁止工具 | 没有 | 没有 | 没有 |
| 上下文快满 | 用到窗口的 90% 时把旧历史压成交接摘要，接着做（`openai_models.rs` 的 `auto_compact_token_limit`） | 剩下不到 16384 个 token 时压缩，留最近约 2 万个 token 的原文（`compaction.ts` 128–129、269 行） | 用到 80% 时压缩，留尾部 16%；压缩前先修剪过大的工具结果 |
| 单个结果太大 | 截掉中间，注明原来多长 | 截到 2000 行或 50 KB | 超过 8192 字符留头 4096、尾 1024；完整结果存盘，告诉模型去哪读 |
| 防编造 | 没找到 | 摘要只写「上面明确出现的」 | 摘要列出没做完的事 |

共同点：循环由模型决定什么时候结束；装不下就压缩旧的、截断大的，接着查；没有一家在资料不够时逼模型作答。

### 要改的方向

只记方向，施工前再细化：

1. **去掉 10 步逼答。** 留一个高得多的安全上限，只防死循环。碰到上限就停下，回复里如实写「还没查完」，不发 `tool_choice: none` 逼答。
2. **放不下时压缩，不整条丢掉。**
   - 单个结果太大：留头尾、截掉中间，注明截掉了多少，提示模型用 `from`、`to` 分页再读。我们的工具已经能分页：搜全书、搜讨论有 `from`，读正文有 `from`、`to`。
   - 这次回复查的东西累计快满：把这次回复里较早的查阅结果压成摘要，接着查。讨论之间的压缩已经有了（[讨论长了压缩成摘要](../../implemented/architecture/2026-10-15-compacting-a-long-talk.md)），这里是一次回复之内。
3. **查不到就明说。** 提示词里要求：资料里没有的，说没查到，不要推测；回答里列出没查到的点。三家都没有这一条，是 Claude 的建议。
4. **「还没查完」的界面。** 要不要给作者一个「接着查」，属于界面改动，按 AGENTS.md 先在原型里做出来给作者看。

## Alternatives considered

- **维持现状。** 最强的理由是一次回复的请求数和用量有确定的上限，界面也已经会写「已达到本次查阅上限」。作者认为它会让模型在资料不够时编造。
- **只把 10 步调大。** 改动最小。没选为主方案：只是推迟逼答，放不下时整条丢掉的问题还在。
- **到上限时拿掉工具，而不是发 `tool_choice: none`。** 原篇已经否掉：前面几轮有工具调用、请求里却没有工具定义，Anthropic 会拒绝；还会改掉前缀，缓存失效。

## Acceptance criteria

- 查阅到安全上限、或者压缩以后仍放不下时，回复不出现查到之外的内容，并写明哪些没查到。
- 单个结果超长时，模型拿到的是截断的结果和分页提示，不是一句「放不下了」。
- 一次回复之内的压缩，不改日志里存的全文。
- 改完以后，原篇的「一次回复」一节同步改，互链本篇。

## Risks

- 去掉固定上限以后，一次回复的请求数和花费没有那么确定。安全上限和每次请求的用量显示要一起看。
- 压缩本身要再调一次模型，压得不好会丢掉关键的原文。
- 提示词要求「明说没查到」，模型不一定照做，要用测试的假模型和真模型各试一遍。
