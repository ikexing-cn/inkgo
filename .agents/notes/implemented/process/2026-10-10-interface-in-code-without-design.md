# Agent Note: 界面直接在代码里改，不再先画设计稿

Status: implemented

## Problem

到 2026-10-10 为止，界面以 Design artifact 为准：改界面先改设计稿，再照着改代码。作者用下来有两个问题：

- 同一个界面做两遍。设计稿是网页，软件是 Go 加 mygo，没有东西能复用；偏差还要同步回去。
- 设计稿是一张张图，不能点。手感好不好，只有在软件里才试得出来；网页的字体、断行、控件和 mygo 也不一样，画得再细也不等于做出来的样子。

## Decision

作者 2026-10-10 决定不再使用 Claude Design，界面直接改代码。

- `AGENTS.md` 的「界面设计以 Design artifact 为准」一节换成「界面直接在代码里改」：
  - 改完渲染截图核对，告诉作者改了什么；作者用测试书（见[测试用的书](2026-10-10-sample-books.md)）打开软件试。
  - 新页面、新的交互方式，动手前先用几句话和作者说清楚；拿不准时列出两三种做法让作者选。
  - 界面文字的写法（日常说法、名称 2–4 字、描述不超过 20 字）原来只在对话里约定，这次写进规矩。
- 颜色、字号、圆角、阴影、间距、行距、图标大小、半透明、控件高度的约束不变，仍由 `go test ./desk` 把关（`TestTokens`、`TestSizeTokens`、`TestNoLiteralSizes`）。这些检查本来就只看 `desk/tokens.css` 和界面代码，不依赖设计稿。
- `desk/tokens.css` 从「设计稿那份的原样副本」变成基准本身：
  - 去掉只有设计稿画板才用的 7 行：`--page`、`--fs-board-title`、`--fs-board-h2`、`--r-window`、`--r-window-win`、两套主题的 `--shadow-board`。
  - 要加一级或改一个值，先和作者说，再改它和 `theme.go` 里的同名常量。
- 删掉只为设计稿服务的工具：`scripts/design/`（`normalize.ts`、`system.ts`、`render.ts`、`rules.ts`、`parts.ts`）、`scripts/verify-design.ts` 和 `package.json` 里对应的四条命令。
- 原来的 Design artifact 留作存档，不删、不更新。里面还没做的「导入稿件」「全书规划」可以参考。

本篇取代[基准色、字号等规范](../architecture/2026-10-09-design-color-tokens.md)里和设计稿有关的部分（设计稿只写变量、设计稿工具、`verify-design`、两份 `tokens.css` 的同步）；那一篇里代码这边的常量、刻度和测试仍然有效。

## Alternatives considered

- **继续设计先行** — 改图之前不动代码，方向错了损失小，几个方案可以并排比较。但图和代码现在都由 AI 来做，改代码并不比改图慢；做两遍和不能试的代价每次都要付。
- **拉一个用完即弃的原型分支，逻辑随便糊，定了再在主线上重做** — 试的时候可以完全放开，不用顾虑测试和数据。但仍然是做两遍，只是第二遍便宜一些；作者权衡后选了直接改。以后遇到要大改、怕弄坏主线的界面，可以再用这个办法。
- **留着设计稿的「设计规范」页当规范的展示** — 字号、颜色有一页能看。但它要靠 `system.ts` 从设计稿的 `tokens.css` 生成，留它就得留整套工具和两份 `tokens.css` 的同步；规范的内容在 `desk/tokens.css` 里带注释写着，够看。

## Consequences

- **收益**：界面改动只做一遍，做完就能在软件里点着试；少了九百多行设计稿工具和「设计稿与代码是否一致」这件要维护的事。
- **代价与已知上限**：
  - 意图和现状不再分开存放：以后看到一处别扭，分不清是当初就这么定的还是做歪了，要靠笔记记下关键决定。
  - 少了作者事先确认的一道关口，小改是先做出来、作者看到实物后再否决。
  - 并排比较几个方案变贵了，只能靠文字描述，或者真的做出来。
  - 存档的设计稿会越来越旧；按它参考「导入稿件」「全书规划」时，要先和现在的界面对一遍。
  - 以前的笔记里提到「设计稿」「照设计稿」的地方没有逐篇改，它们记的是当时的依据。
