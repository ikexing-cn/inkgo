# Agent Note: AI 基建第二轮：回复用满最大输出，按服务商的计数量讨论，回复时照常用

Status: implemented

## Problem

[AI 基建](2026-10-15-ai-infrastructure.md)五步做完，[连真实服务走了一遍](2026-10-15-ai-infrastructure.md#连真实服务走了一遍)以后，留下几件待作者定的事，查的时候又发现几处：

- **截断说不清，也改不了**：讨论、起草各只要 32768 个输出 token，改写、检查 16384，推理也算在里面。拼装时给输出留的却是模型的最大输出（可发送的输入 = 上下文上限 − 最大输出），以 deepseek-flash 为例留了 384K、只要 32K。最高思考程度推理超过上限就截断，提示只有「模型回复被截断」；作者去调大「最大输出」也没用，卡住的不是它。
- **估算偏差大**：要不要压缩、查到的内容还装不装得下，都按估算定，连 DeepSeek 时估多了约一倍；一轮里只扣了查到的结果，模型前几步的话和调用参数没算。
- **回复时整个窗口都灰着**：讨论一回复，导航、新对话、摘取、设置里本作品的模型都不能点。原型里只有发送键不能点。回复可能要好几分钟，作者没法去写正文。
- **一轮最多 5 分钟**：一轮可能先压缩、再查最多 10 步，整轮被 `desk/app.go` 的 5 分钟上限卡住；模型层特意给单个请求留了 15 分钟，最高思考程度光想就可能好几分钟。
- **讨论不知道有哪些章**：`read_prose`、`read_summary` 要完整的章名，模型想读「第九章」得先搜一次。
- **「AI 参考内容」两个数说的不是一回事**：「本次发送约 N」是最后一次请求的估算，「实际用量」是一轮所有请求的合计，查了几次书就差几倍。
- **放弃改写以后键盘去哪里**：原型收起这一行、回到正文；软件里改写要求重新出来。
- 「停止」「取消」和「采纳」在同一个位置；摘要里的「[2]」作者看不懂；设置里「本作品使用」和「本作品用量」只差一个字；压缩时只写「正在思考…」；起草接在后面时，上一段末尾有一小条绿色。

## Decision

作者 2026-10-15 逐条定了（「除了 13 都同意，13 的话，也同意」）。界面上看得见的先做进原型，作者看过（「可以，开发吧」）再写代码，单独提交；不用看的先写进代码。

### 回复要模型的最大输出

- 讨论、起草、改写、检查的请求不写上限，`inference.Model.Complete` 在 `MaxTokens` 为 0 或不小于最大输出时填模型的最大输出。续写（400）和章节摘要（1200）本来就要短，照旧。
- 要的就是最大输出时还被截断，报「回复超出模型的最大输出 N（含思考）；请在设置中「AI」配置里调大」：`model.ErrTruncated` 在 `Complete` 里换成这句。自己要得少的（续写、摘要）照旧报「模型回复被截断」。
- 半截回复照旧丢掉，让作者重试。

### 按服务商的计数量讨论（照 pi）

pi 不估整个请求：上一次回复服务商算的输入就是到那里为止的大小，只给之后新加的部分估算。我们照这个做，系数仍按每字 1.5（pi 的「字符数 ÷ 4」是对英文的）。

- **要不要压缩**：`discussion/compact.go` 的 `measured` 取上一条回复记的输入，减去它当时各部分的估算（`prompt.Size(Sent)`），就是估算差了多少；`due` 把这个差加到这次的估算上。上一条回复没有用量、之后压缩过、设定改过（修订号不同），或者设定一次是整份一次是目录，就不算这个差，退回估算。这次设定要换成目录时也不算：差是按整份量的。
- **查到的还装不装得下**：一步回复之后，下一步的请求 ≈ 这一步服务商算的输入 + 它的输出 + 这次要回给它的结果（估算）。超过模型可发送的输入，这个结果换成「装不下了」，下一步不让模型再调工具（`discussion/engine.go` 的 `respond`）。服务商没回用量时，照旧按拼装剩下的空间（`Context.Left`）。
- 设定发整份还是目录、写作类的请求怎么装，仍按估算：那是在发请求之前，没有计数可用。

### 每次请求的用量记在它自己的事件上

- 查阅那一步的事件（`role: call`）记那一步的用量，回复记最后一步的。原来回复记各步的和，`Usage.Add` 挪到 `workspace` 只给界面加。
- 这样回复的用量和它记的 `sent` 说的是同一次请求，`measured` 才能拿两者比。
- 回复下面「· N token」是这一轮所有请求的和：回复自己的，加上回复同一句话的每个查阅事件（`workspace/events.go` 的 `Spent`）。「AI 参考内容」的「实际用量」暂时也写合计，等下面原型里的改法确认了再改。
- 账本（`.writer/usage.json`）本来就按每次请求记，不变。2026-10-16 起账本换成 `ai-log.jsonl`，见[AI 记录](../feature/2026-10-16-ai-record-and-trace.md)。

### 回复时照常用

- 讨论回复时，只有两样要等：发送和「重试回复」（同一时间只回一句），和切换作品（会换掉整部作品）。换页、换对话、新对话、摘取、加入设定、右栏、设置里本作品的模型和模型服务都照常。
- `desk/app.go` 里仍只有一个任务槽 `a.busy`。`held()` 说的是槽里的活要不要挡住窗口：讨论不挡，获取可用模型照旧挡。
- 回复落在发起它的那段对话里（`talkSession`）。换到别的对话，进行中的那一轮不显示（`replying()`）；回来时还在，回完了就是回复。没存下的话照旧还到输入框，输入框各对话共用。
- 回复中途改了讨论模型，这一轮用原来的：讨论在发送时按当时的设置建好。设置里本来就写着「修改自下次发送起生效」。
- 一轮的总时长不设上限，每次请求 15 分钟的上限在模型层照旧，作者随时能取消。检查的 3 分钟也去掉：它现在要用满最大输出，最高思考程度 3 分钟可能不够。章节摘要的 2 分钟留着：它只要 1200、不推理。

### 章名写不全也找得到

`discussion/tools.go` 的 `book.find` 一档一档找，哪一档只对上一章就是它：

1. 章名完全一样，带不带「」《》都行；
2. 去掉空格和标点以后一样（「第三章 停电」对「第三章：停电」）；
3. 以它开头（「第三章」）；
4. 含有它（「停电」）。

同一档对上好几章，回「对得上好几章：……；写全章名」。一章也对不上，列出共有连续字最多的几章（至少两个字，最多 5 章）；连这样的也没有，照旧叫它照搜全书结果里的写。回复上方那一行写书里的章名，不写模型给的。

### 其余

- **放弃改写**：收起这一行，键盘回到正文，和放弃起草一样。「重新改写」照原型，不再打开改写要求，用原来的要求把同一段再改一次。
- **压缩时**：回复的地方写「正在压缩上下文…」。每份摘要开始写时，`Step` 收到一个没有 ID 的摘要事件，写完收到写好的那个；界面据此切换说法，写完就刷新，「以上 N 轮已整理成摘要」那一行当场出来。刷新以后作者刚发的话已经在日志里，就不再另画一个气泡。
- **起草接在后面**：提议和采纳后的标记都从第一个字起，不含开头和结尾的换行（`editor` 的 `words`）。原来含开头的换行，换行算在上一段末尾，染出一小条绿色。

### 先做进原型、作者看过的

- **半秒内点了不算**：起草、改写写完，这一行换成「放弃」「重新改写／重新起草」「采纳」以后半秒内，点这三个都不算。提议出来的时刻记在那次请求上（`aiRun.shown`），`settled` 按真实时间比，不用重画：半秒以后再点就算。
- **「AI 参考内容」说的是最后一次请求**：「实际用量」写回复自己记的用量，和「本次发送约 N」说的是同一次。这一轮不止一次请求的，标题下面注明「这一轮共 N 次请求，这是最后一次。」N 是这一轮记了用量的查阅事件数加一（`requests`）；这之前的回复各步合在回复上，查阅事件没有用量，算一次，照旧写合计。回复下面的 token 数仍是一轮的合计。
- **摘要里的设定写名字**：「[N]」换成第 N 条的第一个名字，没有名字取第一句开头（最多 16 字），加「」，墨色下划线，悬停有底；点了在右栏打开那一条，等作者决定的在「AI 建议」里（`showEntry`，「查看设定」也走它）。没有这一条的编号照原样写。摘要文字存的还是编号，模型读的也是。
- **设置里改名**：「本作品使用」改叫「本作品的模型」，和「本作品用量」不再只差一个字。

### 连真实服务以后作者定的

下面「连真实服务」看到的几处，作者 2026-10-15 照推荐定了（「可以 都同意。」），代码、原型、`DESIGN.md` 同一次改：

- **别处的提示条留着**：在回复的那段讨论不在眼前时，右上角写「AI 正在思考…」带「取消」；回到它就收起。「不在眼前」原来只算别的页、别的对话、右栏收起或在别的标签；右栏里看着讨论列表、专注写作时也看不到它，`talkShown` 加上这两种。原型补上同一个提示条（`app.js` 的 `toasts` 由 `S.waiting` 推出来，不是 `say` 的一条）；正在做的提示条两边都没有关闭的叉，原型原来有，跟着软件去掉。
- **段落不写成「[N]」**：`read_prose` 给每段标「第 N 段：」，「[N]」只留给设定的编号；讨论规则加一句：提到正文里的某一处，引原话或说在哪一章，不说段号，作者看不到段号。
- **摘要规则的例子**：「比如“见 [12]”」改成「比如“[12]”」，模型不再照搬出「与见 [2] 冲突」。
- **摘要的排法和回复一样**：摘要每一栏的内容走回复的 Markdown（`desk/markdown.go`），列表画成圆点；字号、行距用摘要自己的（`digestText`），设定的名字照旧能点（现在是改写成链接，见[回复和摘要的 Markdown 改用 mygo 的 ui/markdown](2026-10-19-markdown-on-mygo.md)）。栏的标题按「## 」切开（`workspace/events.go` 的 `DigestSections`），不交给 Markdown。标题前的文字作为无标题的一节，标题和正文修剪两端空白；分段不依赖讨论提示词要求的四个标题。

## Alternatives considered

- **保留各自的输出上限，提示里写出这次的上限**：最强的理由是模型失控时花得有限，最坏一次写满上限，claude-fable 写满 128K 约 $6.4。没有用：服务商按实际生成收费，上限要得大本身不多花钱；写死的上限作者改不了，提示说了也白说；拼装时已经给最大输出留了位置。
- **截断时留下已写的部分**（pi 这样做）：最强的理由是不白花已经生成的那些。没有用：用满最大输出以后截断很少见，提示也说清了原因；留半截就要改日志和重试的规则。
- **只补上漏算的，仍按估算**：最强的理由是改动小。没有用：估算本身差一倍，补上漏算的也还是差；服务商每一步都回了计数，用它就准。
- **每次讨论都发章节目录**：最强的理由是模型一开始就知道全书结构。没有用：几百章的书每次要多发几千 token；章名放宽以后，模型最多多调一次工具。**加一个「列出章节」的工具**也一样多一次调用，还多一个工具占规则。
- **回复时切换作品也放开，切换时取消回复**：最强的理由是不挡作者。没有用：回复中途很少换作品，这样会悄悄丢掉一次已经花了钱的回复。
- **一轮放宽到 30 分钟**：最强的理由是网络卡住时有个底。没有用：每次请求已有 15 分钟的上限，一轮最多 10 步，作者看得见进度、随时能取消。
- **放弃改写以后改写要求重新出来**（原来的代码）：最强的理由是改几个字就能再试。没有用：和放弃起草不一致；不想再试的还得再按一次 Esc；同样的要求再试有「重新改写」，换个要求就再点「AI 改写」。

## Consequences

- **收益**：
  - 截断只会是模型自己的上限，提示说得准，作者照着改就有用。
  - 压缩和查阅按服务商的计数，估多一倍时不再白白早压、早停。
  - 讨论回复时作者能去写正文、翻设定、开别的对话。
  - 模型给半个章名也能读到那一章。
- **代价和风险**：
  - **旧记录**：这之前的回复记的是各步的和，查阅事件没有用量。回复下面的 token 数照样对；但 `measured` 拿这个和去比最后一次请求的估算，查过书的旧回复之后第一次发言可能压得早一些。只发生一次，没有迁移。
  - **别处还有提示条**：在别的对话、别的页面时，页面上面照旧有「AI 正在思考…」和「取消」的提示条；原型里那时什么都不显示。作者定了留着，原型补上（见上面「连真实服务以后作者定的」）。
  - **讨论和作者同时改设定**：设定是一条条追加的修订，`Store.Revise` 在作品锁里读了当前设定再追加，不会互相覆盖；没有专门的并发测试。
  - **最坏一次花得多**：上面第一条备选说的那种。
- **测试**：
  - `go test ./discussion`：
    - `TestTurnWaitsForTheReplyOnly`：讨论要最大输出；用满了截断时的那句话；要得少时照旧；

  - `go test ./writing`：`TestDraftShowsWhatItRecords` 查起草要最大输出。
  - `go test ./desk`：
    - `TestTalkLeavesTheRestFree`：回复中换页、换对话、打下一句、开模型菜单都行，发送、重试回复、切换作品点了没反应，回复落在它自己的对话里；别的页、别的对话有「AI 正在思考…」，它自己的对话里没有；
