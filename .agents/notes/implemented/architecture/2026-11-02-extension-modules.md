# Agent Note: 扩展模块与宿主边界

Status: implemented

## Problem

写作功能需要独立开关、可追踪贡献和按书状态，不能靠核心里散落的条件分支管理。

## Decision

核心保留编辑器、章节目录、存储和扩展宿主；功能由 `cmd/inkgo/modules.go` 显式装配。`ext` 管登记、依赖、启停、账和注入，`ext/hostapi` 放宿主的类型及键；扩展公开能力放 `<id>api`。源码边界由 `ext/boundary_test.go` 检查。

`Requires` 连带开关；`Optional` 是已装配但可关闭的关系，不表示包可缺席，仍参与验证与排序。全局开关可被书级覆盖。Setup 记录声明账，生效表只含当前可用项；关闭仍能查看声明。context 的三个贡献点在随包清单中各最多一个提供方。

功能扩展拥有自己的界面和状态，基础扩展提供共享能力。书级状态经 `r.Persist` 保存，本机设置经 `ext.Setting` 保存；数据目录由宿主按扩展 ID 划分。界面规范只见 `DESIGN.md`。

AI 工具的调用经 `ext.Call` / `ext.CallReadPoint` 的注入边界，快照在实际调用的原闭包内检查捕获的 Session；失效时不执行，执行后如实返回结果，不再事后检查并把成功改成失败。`propose_edit` 只有建议确实收下才返回成功。

翻译表随扩展放在 `ext/<id>/<id>text/`，显示函数在当前语言下取词。扩展命名空间隔离仍未落地，见[后续范围](../../proposed/architecture/2026-11-06-extension-followups.md)。

### 设置、数据与可追踪性

扩展宿主本身不开放登记表、开关、账和详情页的注入键，否则扩展可以抹掉自身痕迹。设置外壳归宿主，内容由扩展贡献；声明设置现在只自动绘制 bool 和带选项的 string，其他类型自行绘制。扩展自行决定是否登记导航页及顺序；旧篇记录的原话是「这个可以自由选择是否注册进去，然后注册的顺序是什么，这个应该属于拓展的一部分」。相同页 ID 可以合页，声明及设置项仍保留各自归属。视觉与导航细节见 [DESIGN.md](../../../../DESIGN.md)、`prototype/ext.js` 与 `desk/settings_declared.go`。

书里的 `ext/<id>/` 放扩展拥有的数据；根目录 `ext.json` 放书级开关与设置。本机 `ext.json` 在 works.json 旁，扩展数据在本机 `ext/<id>/`；`.writer/desk.json` 放书级界面偏好，`.writer/ext/<id>/` 放本机才用的按书状态。没有把所有数据放 `.writer`，因为备份和新书 gitignore 会跳过它。核心在扩展关闭时仍会写入的 `history/`、`trash/` 留在书根；旧篇对此数据归属记录的答复是「接受」。快速开发期不迁移旧的设定、大纲数据，样书由 `cmd/sample` 重建。

详情页读声明账，显示哪些贡献、介入、数据和错误；数据大小打开时后台量一次，不在帧里做 IO。错误含时间、阶段、目标和注入归属。覆盖冲突时所有候选停用、默认实现继续，选择 DefaultChoice 表示显式默认、不再算冲突。快捷键按宿主、随包、另装及同层登记先后裁定；失去快捷键的命令仍在菜单中。实现入口为 `ext/injection.go`、`ext/ledger.go` 和 `desk/settings_ledger.go`，界面文案和布局以原型为准。

### 正文与 AI 的归属理由

持久、跟随正文挪动的标记经 marks；临时可计算的选区、查找、AI 提议和设定名字由编辑器绘制。旧篇对这种分法记录的答复是「同意」。这使查找和名字补全不必依赖 marks；批注只排列已有来源的批注。重叠规则见 `prototype/write.js` 正文标记部分和 `desk/prose_marks.go`，不在本篇另定视觉规则。分层缓存和区间查询避免每帧重算所有标记。

起草、改稿建议必须依赖讨论：旧篇比较过讨论关闭时隐藏入口的 A 与连带依赖的 B，最终选择「B」。讨论不反向依赖两者，因此不成环。开讨论经 `talkapi.Service`，可注入操作归 `talk.starters`，提议交接归 `talkapi.Proposals`；已删 AI 名下的临时碰头点与 DeclareSingle。宿主经 Activities 查询活动，不认识具体讨论功能。

用量接收方及 Activation 每次请求开始时捕获，不能在缓存模型句柄时取定，否则用量模块关开后续写不记账，或旧调用写到新实例。写盘失败提示一次，写成功后再失败重新提示。AI 接口的数据类型和 Completer 归 aiapi，不能别名暴露 inference；请求字节回归测试防止拆分改变模型输入。

### 尚未实施与验证入口

外部数据契约、运行时、MCP、安全模式和作者直接写批注尚未实现，见[后续范围](../../proposed/architecture/2026-11-06-extension-followups.md)。批注扩展当前只排已有批注；旧篇保留的功能意向原话是「可以加上，先记笔记，等这一阶段开发完了再弄」。这不表示现在已有编辑入口。

模块清单及实际依赖以 `cmd/inkgo/modules.go` 与各模块 Setup 为准，初拟分法表不再作为另一份清单。`ext/boundary_test.go` 检查 import 与依赖；`desk` 的 extensions、settings_ledger 和 version_extensions 测试检查开关、声明账、冲突与贡献移除。原型按 `prototype/ext/<id>.js` 拆分，公共宿主在 ext.js，正文紧耦合绘制留在 write.js。

## Alternatives considered

- **Go 标准库的 `plugin` 包** — 最强的理由是插件就是 Go，能直接拿宿主的类型。没选：只支持 Linux、FreeBSD、macOS，关掉 cgo 时直接用 stub 返回 not implemented（`$GOROOT/src/plugin/plugin_stubs.go` 的构建条件是 `!cgo`）；宿主和插件要用同一工具链、同一份依赖构建。Inkgo 是 `CGO_ENABLED=0`，还要上 Windows。
- **`init()` 加空白 import 的隐式登记（Caddy、Telegraf 的做法）** — 最强的理由是加模块只动模块自己。没选：顺序藏在 import 里，测试没法只装一部分；模块不多，一份显式清单更好读。
- **HashiCorp go-plugin（子进程加 gRPC）** — 最强的理由是进程隔离，插件用什么语言都行。没选做界面插件：每次调用都跨进程，画界面撑不住。以后做「后台跑、不画界面」的插件（导入、联网查证）可以再看。
- **Yaegi（Traefik 的 Go 解释器）** — 最强的理由是插件作者写的还是 Go。没选：只能写 Go，解释执行慢，解释的代码不经过 `mygo vet`。
- **现在就选定 wasm 或 goja，先做外部插件** — 最强的理由是早一点让外部开发者用上。没选：mygo 说过要出自己的方案，现在选定，以后多半要换；第一层、第二层不管选哪个都得先做。
- **拿 MCP 当插件机制** — 最强的理由是 AI 工具已经都会说 MCP。没选：MCP 管的是 AI 能调用什么（工具、资源、提示词），不管界面；Zed 用它接 context server，也正打算弃用这条扩展路线。
- **扩展只许往预留的位置放东西，不许改别人的界面和行为** — 最强的理由是 [DESIGN.md](../../../../DESIGN.md) 的一致性好守，VS Code 也不给扩展碰 DOM。没选：作者 2026-11-03 要高自定义，允许注入和替换。一致性改由两条守：随软件带的扩展照 DESIGN.md 写、照样走检查；装了别人改界面的扩展是作者自己的选择，详情页写明它改了哪里。
- **设定、大纲、快照、回收站、查找算核心** — 最强的理由是设定、大纲是 AI 上下文和检查的数据来源，快照、回收站防丢稿，拆出去要多绕一层。没选：作者 2026-11-03 定架构上独立于软件；数据来源的问题由 context 解决。
- **只有必需依赖，双方都要的东西全放进前置扩展** — 最强的理由是关系只有一种，依赖不会越连越多。没选：作者 2026-11-03 要可选依赖；「有它更好、没它也行」的功能（导出带上大纲、设定）硬放进前置扩展会多出一堆只为接线的扩展。
- **AI 做成一个功能性扩展，连用量记录一起** — 最强的理由是「关闭 AI」一个开关就够。没选：作者 2026-11-03 定 AI 是前置扩展，只管服务、模型调用和工具登记；用量记录单独一个。关闭 AI 仍是一个开关：关掉 AI，依赖它的连带关掉。
- **前置扩展按需加载，不给开关（Mod Menu 默认藏起 Library）** — 最强的理由是作者不用管它们。没选：作者 2026-11-03 定页面上不要黑箱。
- **服务一出现就自动启用依赖方（cordis 的 `inject`）** — 最强的理由是不用作者动手。没选：开关要看得见，改成显式开关加连带开关，效果相同。
- **设定、大纲的文件留在原处，只把代码挪进扩展** — 最强的理由是已有的书不用迁移。没选：作者 2026-11-03 定快速开发期不考虑向后兼容。
- **只有全局开关** — 最强的理由是简单，「扩展」页只有一层。没选：作者要按书关掉用不着的功能（VS Code 能按工作区停用扩展）。


## Consequences

功能可独立开关，声明账让关闭状态下的贡献仍可追踪；context 和 marks 隔开数据提供方、消费者及编辑器，减少具体功能进入 App 的机会。代价是调用多一层服务或注入，开关变化要重建派生表，换书仍须整轮 Stop/Start，须守住重启和帧耗时测试。

允许注入和替换使一致性不能只靠结构保证；随包扩展遵守 DESIGN.md，装入改变界面的扩展则由使用者选择。可信 Store 仍可写，不是权限隔离。运行时选型尚未完成，未来适配可能要求修改当前 Go 接口，故不承诺第三方稳定 API。
