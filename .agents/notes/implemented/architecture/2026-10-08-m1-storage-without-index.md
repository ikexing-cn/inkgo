# Agent Note: M1 存储去掉 SQLite 索引，读写只走规范文件

Status: implemented

## Problem

M1 在打开作品时重建 SQLite 索引，在 `Search`、`Counts` 之前又全量重扫规范文件刷新索引，但界面从不调用这两个方法：思路池的筛选、搜索、计数都在内存里对 `Ideas()` 的结果做。索引因此没有提速，只多出一个依赖（`modernc.org/sqlite`）和一条“库文件损坏就删掉重建”的恢复分支。同时 `Ideas()` 校验每条思路的来源时都把它所在的会话文件整份重新解析一次，存储层还为“同一轮人先 AI 后”的顺序再读一遍全部会话。另外，独占新建用硬链接实现，在不支持硬链接的 exFAT、FAT U 盘上无法新建任何思路。

本篇部分取代 [M1 实现笔记](../feature/2026-10-07-m1-discussion.md)中关于 SQLite 的段落；该篇其余决定继续有效。[完整产品提案](../../proposed/feature/2026-10-07-idea-pool-discussion.md)中 M2 的检索与向量缓存不受影响。

## Decision

- `workspace` 不创建、不打开 `.writer/index.sqlite`。规范文件（`work.yaml`、`ideas/*.md`、`sessions/*.jsonl`）是唯一数据；`.writer/` 仍随作品创建并写进 `.gitignore`，留给 M2 的向量缓存。
- 一次读取全部思路时用同一个 `scan`：每个会话文件只解析一次，`conflicts`、`supersedes`、`similar` 引用在已列出的文件名里查，不逐个 `stat`。
- 思路按 `created` 排序，时间相同时人先、再按 ID。同一轮的顺序由记账计划决定：计划里的思路已按人先排好，`created` 依次加 1 毫秒。存储层不再读会话来重排。
- 每个公开方法通过 `Store.lock` 加锁、拒绝已关闭的 Store，并重读 `work.yaml`，让手改的分类列表立即生效。
- 独占新建先确认目标不存在，再把写好的临时文件改名过去；目标已存在时返回 `os.ErrExist`。写入协调边界仍是单个应用实例。

## Alternatives considered

- **保留 SQLite，并让界面改用它搜索和计数** — 代码已经写好；提案里 M2 的 FTS5 trigram 检索和相近度比对都要 SQLite，早接入能早发现问题。但每次查询前必须全量重扫文件刷新索引，查询本身不比内存过滤快；M1 规模是几十到几百条思路，内存过滤即时完成。M2 真正需要 FTS5 或向量时，连同增量失效一起设计。
- **保留硬链接独占新建，失败时退回改名** — 硬链接在多进程同时写时也是原子的“不存在才创建”。但 M1 本来就不支持多个进程写同一部作品，两条写入路径只会扩大测试面；exFAT 上永远走退回路径，等于默认就是改名。
- **存储层继续按会话把手工摘取的思路并回原来那一轮** — 摘取的思路和同一轮的卡片挨在一起，原文上下文更连贯。但这要求每次读取都解析全部会话，而思路池的默认视图是待处理队列，新摘取的思路排在最后更容易被看到。

## Consequences

- **收益**：Windows/amd64、`CGO_ENABLED=0` 下 `cmd/poc` 从 25.8 MB 降到 19.7 MB；少一个依赖和一条损坏恢复分支。读取全部思路时，会话文件的解析次数从“每条思路一次”降为“每个会话一次”。作品可以放在 exFAT 或 FAT U 盘上。
- **代价与已知上限**：没有全文索引，搜索是对内存中文本做子串匹配。思路增长到上千条、筛选明显变慢，或 M2 需要语义检索时，重新引入索引，并与向量缓存一起设计失效规则。手工摘取的思路按摘取时间排在最后，不再并入原来那一轮。

## Verification

`go.mod` 中没有 `modernc.org/sqlite`。`go test ./workspace` 覆盖往返读写、手改文件后的严格校验、ID 冲突不覆盖、会话尾部恢复与按创建时间排序；`go test ./discussion` 的 `TestTurnJournalAndReopen` 检查重新打开后同一轮仍是人先、AI 后。
