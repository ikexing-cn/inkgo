# Agent Note: 每次请求由同一个拼装器按模型的上限装，设定装不下时讨论只发目录

Status: implemented

## Problem

这是 [AI 基建](../../proposed/architecture/2026-10-15-ai-infrastructure.md)五步里的第二步 b，接在[上下文上限配在模型上](2026-10-15-model-limits-and-usage.md)之后。

- 讨论（`discussion/context.go`）、续写改写起草（`writing/writer.go`）、检查（`writing/check.go`）、摘要（`writing/summary.go`）四处各自从可用的输入里扣，各自留余量、各自估算每行的开销。设定的拼法 `renderSetting` 和 `oneLine` 在 `discussion`、`writing` 两个包里各有一份。
- 设定装不下时四处都按「新改的优先」逐条截掉，发出去也按新旧排。作者改一条设定，它就跑到最前面，服务商按前缀算的缓存从那里起全部失效。讨论被截掉的条目，模型不知道它们存在。
- 每次请求只记了附带和省略的条目，没记规则的版本、设定的修订号、各部分占了多少，还原不出当时发了什么，也没法和服务商算的实际用量对比。

## Decision

### `prompt` 包

新包 `writer/prompt` 只依赖 `workspace`，不发请求，讨论和写作都用它：

- `Estimate` 从 `discussion` 搬来，算法不变（[按字符估计](2026-10-08-token-estimate-by-character.md)）。
- `Budget` 是一次请求的空间：`NewBudget(room)` 先留 512 给标题和每条消息的开销；`Take` 放得下才记账，`Must` 不管放不放得下都记账（规则、作者的话、纲这些必须发的），`Return` 退回某一部分。每一部分记在一个名字下。
- `Sent` 把账写成记录：规则按全文的 SHA-256 前 4 字节记成 8 位十六进制，设定记修订号（`len(Revisions)`），各部分按固定的先后列出估算的 token。只记这些，不存请求全文。
- 设定只有一种拼法 `Render`：按位置分段，正文按作品分类的顺序、同一分类按加入的顺序，已放弃和悬而未决也按这个顺序。这个顺序只在设定本身变了的地方变，前面的部分缓存照样命中。`Fit` 是装不下时逐条挑：新改的优先，挑中的仍按 `Render` 的顺序发。
- 条目的写法两种：`Whole` 是全文一行，`Short` 是目录行「分类 · 第一个名字：第一句」，没有名字就是「分类：第一句」。第一句到第一个「。」「；」或换行为止（不含），或到第一个「！」「？」为止（含），超过 60 字截断加「…」。

记录的类型在 `workspace`：`Sent{Rules, Setting, Parts}`、`Part{Name, Tokens}`，部分的名字是 `PartRules`、`PartSetting`、`PartIndex`、`PartOutline`、`PartRecap`、`PartTalk`、`PartProse`、`PartInput`，`Parts` 是它们的先后。讨论回复的事件、写作的 `AIRecord`、`.check.json`、`.summary.json` 各多一个 `sent`。

### 讨论

请求的先后是：规则 → 设定 → 最近的对话 → 作者这次的话（带着附上的正文）。压缩摘要（第 d 步）将排在设定和对话之间。

装的先后不同于发的先后：

1. 规则和作者的话必须放下，放不下报「当前发言超出模型的上下文上限；请缩短，或在设置中「AI」配置里调大上下文上限」。
2. 先为设定的目录占位。目录也放不下，报「设定的目录超出模型的上下文上限，请在设置中「AI」配置里调大上下文上限」。
3. 附上的正文：纲必须放下，光标前的正文从开头截到放得下为止。纲放不下也报第 1 条的错。
4. 最近的对话：至少四轮，记账员还没整理的轮次全放，从新往旧放，放不下就停。
5. 退回目录的占位，整份设定放得下就发整份，否则发目录。

整份设定包括正文、已放弃、悬而未决三处，不再逐条省略：要么全发，要么全发目录。目录开头一句「设定较多，这里只列目录：每条的分类、名字和第一句。」。讨论里的条目记录（事件的 `context`）每条一项：正文直接写，另两处前面加「已放弃：」「悬而未决：」，目录时写目录行。

### 写作、检查、摘要

不用工具，设定装不下时照旧逐条截掉、新改的优先，只是都换成 `Budget` 记账：

- 续写、改写、起草的系统提示改成「写作规则 → 设定 → 这次的任务」，任务挪到设定后面，三种操作共用前面那段。设定只发正文和已放弃，空着时只说「设定文档还是空的。」（原来是「设定正文：（还没有）」）。
- 检查的设定按 `Ordered` 的顺序编号（分类的顺序，同一分类按加入的顺序，已放弃的和正文的混在一起排），不再按新旧。
- 摘要只有规则和正文，也记 `sent`，设定修订号不写。

### 「AI 参考内容」

照原型（2026-10-15 确认）：

- 「本次发送约 N token」，下面一行各部分「规则 1.1K · 设定 12 条 3.1K · 之前的对话 7.5K · 本次发言 40」，再下面「实际用量：输入 9.9K，其中缓存命中 6K；输出 268」，没命中缓存时不写中间那句。
- 附上的正文（所在章、章纲、光标前多少字）照旧打勾列出。
- 「附带全部 N 条设定」加每条打勾；发目录时是「设定较多，本次只附目录」，每条不打勾。
- 原型原来只列设定正文。DESIGN.md「模型看到的，作者也看得到」比原型优先，所以原型和软件都把已放弃和悬而未决也列出来，原型跟着改了，走查的「what was sent」「a setting too big to send whole」查这几条。
- 之前的回复没有 `sent`：不显示各部分和用量那几行，有省略的条目时标题照旧写「回复时附带 N 条设定，因上下文上限省略 M 条」。
- token 数用新的 `tokens.Round`：一千起写 K、M、B，留一位小数，和原型的 `tokens` 一样。

原型目录那一栏下面还有一句「目录只有分类、名字和第一句；需要时 AI 会查全文。」。这一步讨论还没有「查设定」，软件先不写这句，第 c 步加上工具时一起加。

## Alternatives considered

- **讨论的设定也逐条截掉，不发目录**（原来的做法），**或者装不下就报错**：截掉的好处是总能发出去，发出去的都是全文；报错的好处是简单明白。没有用：截掉以后模型不知道还有哪些条目，会和被截掉的设定冲突；报错逼作者调大上限，而有了「查设定」，只发目录就能工作。作者 2026-10-15 定了「动态装载让模型自己调工具去查」。
- **按比例给各部分分预算**（比如设定最多占 40%）：最强的理由是哪一部分都不会把别的挤光。没有用：比例很难定，作者也难以理解；有了工具，正文片段由模型自己去取，不必预先分一块。
- **存每次请求的全文**：最强的理由是最好查。没有用：每次几万字，作品文件夹会涨得很快；记了规则摘要、设定修订号和各部分用量，结合代码和设定历史就能还原。
- **整份设定优先于之前的对话**：最强的理由是设定是作者定下的，对话只是过程。没有用：对话是这次在聊什么，丢了模型接不上话；设定发目录还能查全文，对话没有这条退路。
- **规则版本写成手动递增的数字**：最强的理由是读起来直观，和提案的「版本号」一致。没有用：改了规则忘记加一，记录就错了，没有办法发现；摘要值不会忘，要对应到代码时在 git 历史里找同一段文字。
- **`Estimate` 和拼装器留在 `discussion` 里**：最强的理由是改动最小，`writing` 本来就引用 `discussion`。没有用：拼装器不属于讨论，写作只是要它的估算和设定，而 `discussion` 还带着引擎和记账员；单独一个只依赖 `workspace` 的包，界面也能放心引用。

## Consequences

- **收益**：四处只剩一套算法和一种设定的拼法。设定和规则排在最前，顺序只随设定的修改变，同一本书的请求前缀稳定，缓存命中可以拿用量里的 `CacheRead` 核对。每条回复记了各部分的估算和实际用量，估算偏多少看得出来。讨论不再悄悄丢条目。
- **代价**：设定大到只发目录时，这一步模型拿不到全文，要等第 c 步的「查设定」；在那之前只能靠第一句。检查的编号顺序变了，旧的 `.check.json` 不受影响（它存的是条目 ID，不是编号）。每个事件和记录多存一小段 JSON。
- **测试**：`go test ./prompt` 的 `TestEstimateCountsCharacters`（从 `discussion` 搬来）、`TestBudgetRecordsItsParts`（记账、退回、先后、规则摘要、修订号、放不下）、`TestTheSettingReadsInAStableOrder`（整份和目录的写法与顺序、条目记录、空设定、装不下时留新的）；`go test ./discussion` 的 `TestContextBudget`（刚好放得下发整份、少一个 token 发目录、对话挤掉整份、作者的话太长和目录太大的报错、空设定）；`go test ./writing` 里起草的设定在任务前面、记录有各部分，检查按分类顺序编号并记 `sent`；`go test ./desk` 的 `TestWhatWasSent`（整份、目录、旧回复三种样子）；`go test ./tokens` 的 `TestRound`；`npm run verify-prototype` 的两步。
