# Agent Note: 菜单都由软件自己画，不再用系统菜单

Status: implemented

## Problem

软件里的菜单原来都是系统菜单（mygo 的 `Element.Menu`、`Element.ContextMenu`）：正文和章节树、对话的右键菜单，侧栏作品名、讨论模型、书架和右栏「···」点开的菜单。Windows 上是系统那套灰底的样子，和别的浮层（「更多」、待处理、备份）不是一个长相；原型里这些菜单都是自己画的。

作者 2026-10-12 的原话：「右键的时候，原型是自定义的好看的，软件的不是，把软件的优化成和原型的一致」。

[右栏](2026-10-10-right-pane.md)那篇当时选了系统菜单，理由是「软件里其他菜单都是系统菜单，键盘和读屏是现成的」。这一篇取代那个选择。

## Decision

- 菜单在 `desk/menu.go`，全软件一份，同一时间只开一个（`App.menu`）：
  - `contextMenu(c, el, key, build)`：在 `el` 上按右键，菜单的左上角放在指针那里；焦点在 `el` 里时按菜单键或 Shift+F10，放在它下面。
  - `dropMenu(c, b, key, place, build)`：点按钮 `b` 打开，再点收起；`place` 定它挂在按钮的哪一边、多宽。
  - `build` 里一行一句：`m.Item("重命名").Hint("F2").Disabled(…).Do(a.renameOpen)`，`Do` 给的是点了这一行要做的事；另有 `m.Separator()`、`m.Submenu(…)`、`Hint`（右边的快捷键或条数）、`On`（正在用的那一项）、`m.Head`（一组的小标题）。
  - 2026-10-14 起，`build` 只把各行**记下来**，不画：`menu` 是一份清单，每行是数据（写的什么、提示、能不能点、是哪一种）加上点了要做的事（`Do` 给的那个函数）；里面没有 `*ui.Context`，也没有 `*App`。画由 `App.menuRows(c, build, …)` 一处做：叫 `build` 列出各行，照清单画；哪一行被点了，先把菜单关掉，再叫那一行自己的函数。`build` 一帧只跑一遍。
    - 没给 `Do` 的行（「作品」菜单里正开着的那一本）点了只关菜单。
    - `build` 里要自己画东西（「视图」菜单里的外观三选一），用 `m.Draw(func(c *ui.Context))` 记成一行，画到那里时才叫它，`Context` 是画的那一方递进来的。
    - 最早是 `menu` 里存着这一帧的 `*ui.Context`，每个方法当场画一行，`if m.Item(…).Chosen() {…}` 当场回答有没有被点。那样 `mygo vet` 会报（它不许结构体里放 `Context`），曾经在检查脚本里单独放行；作者 2026-10-14：「应该可以通过软件工程设计优化吧」。
    - 同一天先做过一版（提交 `a290e9e`）：行已经是只记不画，但为了不改调用处留着 `Chosen()`，办法是哪一行被点了就把 `build` 再跑一遍，让那一行的 `Chosen()` 回答「是」。作者看了说：「我的直觉告诉我这样写非常的workaround」。说得对，当天改成现在这样，理由在下面放弃的方案里。
- 样子照原型的 `.pop`、`.pop-row`：行高 `hRow`，圆角 `rCard` / `rControl`，阴影 `pop`；不能点的行整行 40% 透明。「更多」菜单的行改用同一个 `popRow`。
- 右键菜单宽 200，整个留在窗口里：先不透明度 0 画一帧量出高度，下一帧再放。旁边那一列（「加入名字表」）宽 120，指针移到那一行上就打开（点它、按 Enter 也行），移到菜单别的行上收起；它和打开它的那一行平齐，右边放不下就开在左边，下面放不下就往上挪。原型原来要点一下才开，一起改成移上去就开。
- 右键菜单开着时，底下垫一层看不见的东西接住别处的点击：点别处只关菜单，不会顺带点到下面的东西。原型也是这样。挂在按钮上的菜单用 `ui.PopoverBase`，和别的浮层一样，点别处关掉并且那一下照常生效。
- 键盘：菜单打开时第一行能点的拿到焦点，上下键在行间走，Enter 选，Esc 关；关掉后焦点回到原来的地方。Tab 被菜单接住，什么也不做，焦点不会跑到菜单外面去。
- 菜单的三块（垫在底下的那层、菜单、旁边那一列）各有名字（`c.Key`）。mygo 里一个元素是谁，默认看它是父元素的第几个孩子；浮层都挂在同一个父元素下，前面多出或少掉一个浮层，后面的就对不上号，会拿到别的元素上一帧的位置和大小。菜单靠上一帧的高度算自己放在哪，拿错了就被挪走。
- 编辑器（`editor/`）不依赖 `desk`，画不了这个菜单。`Options.OwnMenu func(x, y float32)` 设了，编辑器就不出系统菜单，只告诉宿主在窗口的哪里要菜单，菜单由宿主画；`Cut`、`Copy`、`Paste`、`Marked`、`Unmark` 公开给它用。`Options.Menu`、`Options.OwnMarks` 没有地方用了，删掉。不设 `OwnMenu` 的（`cmd/poc` 不带 `-work` 的那个试编辑器的窗口）仍是系统菜单。
- 各处照原型改了的：
  - 侧栏作品名：只列别的作品，上面写「切换作品」，右边是体裁；原来连当前这本一起列、打勾。
  - 讨论模型：原来是「模型 › 服务 › 模型」「思考程度 ›」三层，改成一列，模型和思考程度各一组；有不止一个服务时，每个服务的模型上面写服务名。
  - 章节树：「移到」原来是子菜单，改成同一列里的一组，不列它现在所在的地方。
  - 右栏「···」：条数放在右边，不再写进名字里。
  - 书架「···」：「打开所在文件夹 / 重命名… / 从书架移除」，第一项原来按系统叫「在资源管理器中显示」。
  - 正文：选区上浮的「AI 改写 / 加入设定」在菜单开着时不显示。「移除此处标记」原来一直在、不在标记上时发灰，改成只在标记上才出现。
- 正文菜单里的「剪切 / 复制 / 粘贴 / 全选」原型没有（原型的正文不能改），软件留着，并且在原型里补上：复制和全选是真的，剪切和粘贴提示一句「原型的正文不能修改」。

## Alternatives considered

- **留着系统菜单** — 键盘操作、读屏、超出窗口时的摆放都是系统做好的，不用自己写，也不会比系统的行为少一块。不用：作者要的就是和原型一个样子；自己画的这份键盘能用，角色标了 `RoleMenu` / `RoleMenuItem`。
- **只换右键菜单，点按钮打开的仍用系统菜单** — 作者说的是「右键的时候」，改动小一半。不用：两种菜单会并排出现在同一页（右栏「···」和正文右键），一个系统样子一个自己画的，比全是系统的更乱；原型里它们也是一个长相。
- **编辑器自己画菜单** — 编辑器已经自己画了补全的小浮层，`cmd/poc` 的试验窗口也能跟着变样。不用：菜单的颜色、圆角、阴影都在 `desk` 的调色板里，编辑器要么依赖 `desk`，要么抄一份；菜单里大半的项（改写、引用、名字表、伏笔）本来就是宿主的。
- **右键菜单也用 `PopoverBase`，点别处时那一下照常生效** — 少一层垫着的东西，和别的浮层一个行为。不用：`PopoverBase` 要挂在一个元素上，右键菜单跟的是指针；原型和系统菜单都是点别处只关菜单。
- **`menu` 里留着 `*ui.Context`，在检查里放行这一处**（2026-10-14 上午的做法） — 一行都不用改，运行上也没有问题：构建器当场造、画完就丢。不用：`mygo vet` 只认工具包自己的类型，放行以后 `menu`、`menuItem` 被存起来或带进后台任务它查不出来；检查脚本还要养一张放行表。
- **每个方法都把 `c` 传进来**（`m.Item(c, "重命名").Chosen(c)`） — 最直接，谁在用 `Context` 一眼看得见，也不用改成先记后画。不用：每写一行菜单都多写两遍 `c`；旁边那一列本来就得等菜单画完才能画，「当场画」做不彻底。
- **留着 `Chosen()`，被点的那一帧把 `build` 再跑一遍**（`a290e9e` 做的那一版） — 调用处一行都不用改；工具包自己的系统菜单 `ui.Menu` 就是这么做的（菜单打开时跑一遍，选了以后再跑一遍，按「第几项加写的什么」认回那一项）。不用：工具包那样做是因为系统菜单由系统去显示，选了哪一项要过后才知道，只能再跑一遍去找；自己画的菜单当场就知道点的是哪一行，没有这个难处，却背上了它的后果：`build` 得能跑两遍（只许列行，动作只许写在 `Chosen()` 的 `if` 里，编译器不管）；两遍列的行不一样时要有一道防错；`Chosen()` 读起来是「被点了」，实际是「现在是第二遍，而且轮到我」。这些都只是为了少改 57 行调用处。
- **点了以后记下是哪一行，下一帧再让 `Chosen()` 回答** — 一帧只列一遍，调用处也不用改。不用：还是靠再跑一遍 `build` 去找那一行，上一条的毛病都在，动作还晚一帧。
- **第一帧按行数估高度** — 不用空画一帧。不用：行高、分隔线、小标题各不一样，估出来的数要跟着菜单内容改；原型就是估的，章节菜单因此伸出过窗口（这次一并改了）。

## Consequences

- **收益**：
  - 菜单和别的浮层一个长相，深色模式下也是。
  - 菜单能进截图了（`SHOT=dir go test ./desk -run TestShotMenus`），以前系统菜单无头测试截不到。
  - 测试里点菜单用 `pick(tt, "加入名字表", "人物")`、看菜单有哪几行用 `rows(tt)`（`desk/menu_test.go`），行的标签是「菜单-」加上字。
- **代价与已知上限**：
  - 键盘只有上下键、Enter、Esc；系统菜单的按首字跳到那一项、左右键进出子菜单没有做。
  - 软件里别的浮层（选区上的两个按钮、记伏笔的小框）还是按次序认的，没有名字。它们不靠上一帧的大小摆位置，没有看到问题。
  - 读屏读到的行名带「菜单-」这个前缀：为了测试里和页面上同名的按钮（「新建章节」）分得开。
  - 右键菜单打开的头一帧是看不见的（量高度），多画一帧。
  - 禁用的控件工具包自己会再乘 0.5，`Opacity(opacityDisabled)` 实际只有 20%。加了 `pale(b)` 把它算回 40%，全软件禁用的按钮都比原来深了一倍。
  - 同名的菜单靠 `key` 区分：两个地方用了同一个 `key`，会一起打开。
  - 57 行 `if m.Item(…).Chosen() {…}` 改成了 `m.Item(…).Do(…)`；前面带条件的（`if n.Folder && m.Item(…).Chosen()`）改成外面套一层 `if`。
  - 一行要做的事是在 `build` 跑完以后才做的：它用到的变量要是在 `build` 后面又被改过，做的时候看到的是改过以后的值。57 处逐个看过，没有这样的；循环里的行各有各的循环变量（Go 1.22 起每轮一份）。
  - 标题栏的四个菜单本来就把要做的事留到标题栏画完（`act`），现在写成 `Do(later(…))`。
  - 各行在 `build` 跑完以后才画：某一行被点时，它后面的行这一帧还是照动作之前的样子画的（原来是照动作之后的样子）。这一帧菜单正在关，看不出区别。

## Verification

- `go test ./desk -run 'TestTextMenu|TestMenuRows'`：右键后没有系统菜单、行的次序、菜单左上角在指针处、窗口角上不伸出去、旁边那一列在窗口底下不伸出去、点别处只关菜单不换页、Esc、菜单键、不能点的行点了没反应并且是 40% 的深浅。
- 2026-10-14 构建器改成只记行、每行带着要做的事以后：`TestMenuListsItsRows`（列的时候不画、不做；要做的事跟着行走）、`TestMenuRowDoesItsPart`（点了只做一次，做的时候菜单已经关了，把顺序倒过来测试会失败；`build` 每帧只跑一遍，菜单关了就不跑；不能点的行不做也不关；没给 `Do` 的行只关菜单）；测试里原来 15 处点菜单的地方不改就过。三版各渲染一遍全部 85 张截图逐像素比（最早的、`a290e9e` 的、现在的）：13 张开着菜单的图里 11 张完全一样，另两张只差侧栏上那个时间；其余有差别的图，同一份代码跑两遍也差在同样的地方（时间、临时路径、悬停）。`mygo vet` 对三个包都没有报告。没有在真的窗口里点过。
- 作者 2026-10-12 在真的窗口里看到旁边那一列伸出窗口下沿，改了以后加进了上面的测试。
- 作者 2026-10-13 在真的窗口里看到：旁边那一列先画在窗口最上面再下来；菜单开着时按 Tab，菜单跑到左上角。原因都是上面说的认错了元素：那一列头一帧拿到的是别的浮层的高度（整个窗口高），被当成放不下、挪到了顶上；按 Tab 时多出一个浮层，菜单拿到了垫底那层的大小。无头测试一次画到稳定为止，只看最后一帧看不出来；`TestMenuStaysPut` 在每一帧开画前记下上一帧菜单和那一列在哪，去掉名字它就不过（那一列有一帧在 y=13）。同一个测试也查指针移上去打开、移开收起、点一下不收起。
- 截图和原型走查存下的 `17-menu`、`83-name-menu`、`31-tree-menu`、`33-book-menu`、`60-model`、`07-menu` 逐张比过。没有在真的窗口里逐个点过。
