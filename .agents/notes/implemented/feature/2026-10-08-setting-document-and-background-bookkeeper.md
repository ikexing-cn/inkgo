# Agent Note: 设定文档取代思路卡片，记账交给后台 agent

Status: implemented

## Problem

M1 每轮对话串行：先回复，再把这一轮拆成思路卡片，再查冲突，全部做完作者才能接着说话；然后提示"整理出 N 条思路，M 条等你决定"，要作者逐张留下、待定或放弃。作者试用后的反馈是：

- 想要的是"无感问答、自动整理"：作者只管和 AI 讨论，整理在后台完成，不要每轮都做取舍的家务。
- 卡片是零散的列表，想知道"这本书现在是什么样"，作者得自己在脑子里拼。

本篇取代 [M1 讨论](2026-10-07-m1-discussion.md)中关于卡片、状态流转、串行记账和冲突检查的决定，[M1 存储](../architecture/2026-10-08-m1-storage-without-index.md)中关于 `ideas/*.md` 的部分，以及[完整产品提案](../../proposed/feature/2026-10-07-idea-pool-discussion.md)中"思路是基本单位""思路池是唯一依据""从思路到设定"三节的方向；这几篇的其余内容不受影响。讨论规则的新写法见[讨论规则改为合作者口吻](2026-10-08-talk-rules-as-collaborator.md)。

## Decision

### 两个 agent

- **聊天 agent**（`discussion.Engine`）：只负责回复。发送一轮只等回复，回复落盘后作者就能接着说。
- **记账 agent**（`discussion.Bookkeeper`，由 `discussion.Worker` 调度）：纯后台，把讨论沉淀进设定文档，不打断聊天；界面上只有一个小圆点表示它在整理或上次失败了（见"界面"）。模型和推理等级用作品配置里的"记账"一项，留空沿用讨论。
- 删除单独的冲突检查步骤（`discussion/conflicts.go`），矛盾在记账时处理。

### 设定文档

一部作品一份文档，由条目组成。每条一句可以独立成立的设定。条目在三个位置之一：

- **正文**（`body`）：按作品分类分节，只放作者拍板的内容。
- **悬而未决**（`open`）：作者还没表态的 AI 点子，以及推断出来、需要作者裁决的矛盾。
- **已放弃**（`dropped`）：作者不要的内容。AI 不会再推荐，作者可以把它移回来。

每条记录：分类、文字、出处（会话、消息、该消息里的一段原文，可以有多处），以及是否被作者亲手改过（`Author`）。

出处也可以指向正文：作者在[正文页](2026-10-08-writing-page-and-chapters.md)选中一段"加入设定"时，出处是章节节点 ID 加原文（`Source.Chapter`），不带会话和消息。加入时原文必须在那一章当前的正文里；重放修订时不再核对，因为正文本来就会继续改。

作者也可以在[写作时的讨论侧栏](2026-10-08-discussion-beside-the-prose.md)里引用正文。引用存在发言的 `quotes` 里；记账和讨论看到的发言是 `Event.Said()`，即每段引用以"【引用正文《章名》】"开头，后面接作者的话。出处的原文按 `Said()` 核对。原文落在某段引用里时，出处在会话和消息之外再标上那一章（`Source.Chapter`），设定条目悬停时可以"在正文里找到来源"。这类出处只核对发言，不核对章节当前的正文。记账规则多了一条：引用的正文算作者写下的内容，但只记作者借它说明或认定的设定，不把情节逐句记成设定。

### 修订

- 文档的唯一来源是只追加的 `setting.jsonl`。每次记账、每次作者亲手改动各算一次修订（`workspace.Revision`）。
- 记账修订还记录：处理的会话、覆盖的消息范围（`From`、`Through`）、模型、推理等级、思考过程。
- 失败也记一次修订：只有失败原因（`Failed`）和覆盖范围，没有操作。重试成功的修订用 `Redo` 指向它。
- 打开作品时把全部修订重放一遍，结果保存在内存里。磁盘上不另存快照。
- 每个条目带内存中的 `Rev`，即最后改动它的修订序号；修订的 `Base` 是记账开始时看到的序号，用于并发判断。
- 会话文件和设定文件共用 `workspace/jsonl.go` 的读写与尾部恢复：最后一行写了一半时丢弃该行，前面的行照常读取。

### 记账 agent 的输入和输出

- **输入**：
  - 当前文档，条目用本次请求内的短编号 `e1`、`e2`……；
  - 作品分类；
  - 这批要处理的消息，用 `m1`、`m2`……编号，标明是作者还是 AI 说的；
  - 这批之前已整理过的最多两条消息，标 `earlier: true`，只用来理解"第二个方向"这类指代，可以被引用。
- **输出**：严格 JSON 的操作列表，只有三种：
  - `add`：新增条目，指定位置、分类、文字和出处；
  - `edit`：改写一条的文字；
  - `move`：把一条移到另一个位置或分类。
- 附加字段：`accepted` 是作者表示接受的原话，`because` 是作者改口或表态的原话。

### 程序校验的规则

模型的判断只决定"做什么"，"能不能做"由 `Bookkeeper.check` 把关：

1. 每处原文必须出现在它指向的消息里。先逐字比对；对不上时忽略空白、Markdown 标记和引号再比一次，命中就把原文换成消息里的原样文字再保存。
2. 新增到正文时，出处必须来自作者的话；出处来自 AI 的话，还要有 `accepted`。新增到已放弃要有 `because`。
3. 改写或移动正文、已放弃里的条目，以及作者改过的条目，必须有 `because`，并引用作者的原话。推断出来的矛盾只能新增一条"悬而未决"。
4. 分类必须是作品已有的。

整批全部通过才写入。没通过时，把错误列表（含对不上的那段原文）回给模型重给一次；仍不合格，这次尝试就算失败。

### 并发

`Store.Revise` 写入记账修订前逐条检查：要动的条目 `Rev > Base`，说明这期间作者改过它。这条操作就记进 `Skipped`，改为新增一条"悬而未决"，写明"整理时想改成……，但你刚改过这一条"。其余操作照常写入。作者的修改永远优先。

### 调度

- 打开作品、改了模型设置、任何前台请求（包括发送一轮）结束时，`App.kick` 唤醒 worker。最初只在打开作品时唤醒，作者聊了四轮设定仍是空的；`TestBookkeeperFillsTheSettingInTheBackground` 现在按发送的路径写入一轮，不再手动唤醒。
- 同一部作品只有一个 worker；它在跑时到来的唤醒会合并，下一轮把积压的轮次合成一批。
- 积压的轮次一次放不进[预算](../architecture/2026-10-08-token-estimate-by-character.md)时，从最早的轮次起截到放得下的最后一条回复，剩下的下一批处理；只剩一轮仍放不下，就去掉附带的前一轮。一轮本身就超出预算才算失败。
- 一个会话处理到哪条消息，由覆盖它的最近一次修订决定，失败的修订也算。只处理到最后一条 AI 回复，还在等回复的发言留到下一批。
- 失败后按 10 秒、1 分钟递增重试，共 3 次。仍失败就写失败修订，后续轮次继续往下处理。
- 每次尝试最长 5 分钟，网络卡住也不会让 worker 一直停在那里。
- worker 把每次尝试的开始、用时、结果和出错原因追加到作品的 `.writer/bookkeeper.log`，只保留最近 400 行，供排查。
- `Worker.Busy` 从发现有待整理的轮次起、到这一遍做完（含重试和等待）为真，开始和结束时都通知界面。
- 关闭作品时取消在跑的记账；没写入的批次下次打开再补。

### 聊天 agent 看到什么

- 设定文档：正文按分类列出，加上已放弃和悬而未决。超出预算时按"正文、已放弃、悬而未决"的优先级、同一位置新改的优先保留，省略的记入快照。
- 最近 4 轮对话原文；记账还没处理的轮次不管多早都放进去。
- 每条回复仍保存当时实际给模型看的条目快照，供"AI 看到了什么"回看。

### 界面

- 右侧栏是设定文档（`desk/setting.go`）：
  - 按分类折叠，"悬而未决"和"已放弃"在最底部，"已放弃"默认收起；
  - 整栏可以收起，状态按作品存在 `.writer/desk.json`。
- 作者可以直接改文字和分类、新增条目、放弃或移回；"悬而未决"的条目可以一键放入正文。这些都记为作者修订。
- 记账刚加或改的条目以墨色淡淡高亮，3 秒内淡出。界面不再用紫色品牌色，链接和"开着"的按钮都用墨色，照设计稿。
- 栏顶的"整理历史"逐次列出修订：
  - 写明谁改的、改了什么；
  - 记账修订可以展开看思考过程；
  - 失败的修订显示原因，没重试过的有"重试"。
- 后台整理的唯一迹象是一个 7 像素的圆点（`bookDot`），在设定栏标题右侧；设定栏收起时在聊天顶栏的"展开设定"旁：
  - 整理时用品牌色缓慢呼吸，1.8 秒一次，每 90 毫秒重绘，不按帧刷新；
  - 最近一批记账失败且没有重试成功时变成警告色，后来的批次成功就消失；
  - 悬停说明"正在整理设定"或"上次整理没成功，点开看看"，点击展开设定栏并打开整理历史；
  - 没在整理、也没有失败时不显示。
- 聊天区去掉"整理出 N 条思路"提示；"摘取原文"改为"加入设定"，把选中的原文作为作者条目加入正文。

### 存储格式

- schema 升到 2：
  - `work.yaml` 只改版本号；
  - 会话文件只剩消息事件，没有 `kind`、记账事件和 `idea_ids`；
  - 新增 `setting.jsonl`。
- 不做迁移。打开 schema 1 的作品时提示"这是旧版本的作品（schema 1，思路卡片），没有迁移，请新建作品"。
- 删除 `ideas/` 目录及思路卡片相关的类型、状态机、相近标记、冲突字段和撤销。
- 删除仍有条目使用的分类时，这些条目随一次作者修订移到"其他"。

## Alternatives considered

- **AI 维护一整篇散文式文档** — 读起来最像成稿。但 AI 每次改写段落都可能顺带改掉作者没让动的句子，单句也标不了出处；逐条存储才能精确知道动了哪句，复盘、回滚、保护作者的修改都靠这个粒度。
- **记账 agent 用多步工具调用** — 大多数 harness 让聊天 agent 边聊边用工具记忆（LangMem 的记忆工具、MemGPT 一类），能自我纠错、按需查询。但后台整理记忆的系统，主流是一次提取再给出操作（Mem0 的 ADD/UPDATE/DELETE/NOOP、LangMem 的后台 manager）；整份文档放得进上下文，不需要多步查询；一次返回的整批操作也便于整批写入或整批丢弃。失败时加一轮"把错误回给模型修正"，补上自我纠错。以后如果需要翻历史、跨文档查资料，再升级为工具调用。
- **把文档快照另存到磁盘** — 打开作品不用重放全部修订，修订很多时更快。但快照和修订会出现两份真相，要处理不一致和手改；测试阶段修订只有几十到几百条，重放在毫秒级。修订数到上千、打开明显变慢时，再加带校验的快照缓存。
- **原文只认逐字匹配** — 规则最简单，出处绝对可信。但真实运行中 DeepSeek 引用 AI 回复时常常丢掉 `**`、去掉引号或合并空格，两轮里就有一批因此失败。只放宽这几类字符，并把保存的原文换回消息里的原样文字，出处仍然能在原消息里逐字找到。
- **只给记账看新消息** — 输入最短，不会重复整理。但作者说"第二个不错，就这么定"时，"第二个"在上一条 AI 回复里，看不到就无法落到正文。附上前两条消息并标明已整理过，代价是每批多几百字。
- **保留卡片作为底层，文档只是视图** — 不用改存储，M1 的记账重放和状态机都能复用。但这样要同时维护两套模型；条目自带出处已经能支撑复盘，作者也确认现在是测试阶段，不需要兼容旧数据。
- **作者自己说的话直接算"留下"，仍然用卡片** — 改动最小，又能免掉一半家务。但产出仍是零散列表，"自动整理思路"没有实现；作者看过对比后选了设定文档。
- **等作者停下来再统一整理** — 一次看到更多上下文，调用次数也少。但作者边聊边看文档时，文档会一直落后；改为每轮触发、积压合批。
- **完全不显示后台状态**（最初的约定）— 最贴近"无感"：聊天区和设定栏都不会因为整理而多出任何东西，作者的注意力只在对话上。但作者试用时，第一批 10 条消息在推理等级"高"下想了约 1.4 万字、用了三分半，界面毫无变化，作者以为设定丢了、发送也失败了。作者同意加一个不带文字的圆点：平时看不见，需要时一眼能分清"在整理"和"出问题了"。
- **记账在前台串行**（M1 现状）— 结果立刻可见，失败也能马上提示。但作者每轮都要等两三次模型调用，这正是"不无感"的来源。

## Consequences

- **收益**：
  - 发送一轮只等一次模型调用。
  - 作者不再逐张处理卡片，右侧直接是"这本书现在是什么样"。
  - 每处改动都能在历史里追到哪一轮、谁改的、当时怎么想的。
- **代价**：
  - 每轮多一次后台模型调用，合批只能部分缓解；作者可以给记账配一个便宜的模型。
  - 旧作品打不开，要新建。
- **已知上限**：
  - 圆点只说明在整理，不说明要多久。推理等级高时一批可能要几分钟；整理用低等级会快很多。
  - 记账可能误读作品。附作者原话的规则挡住了凭空写进正文，挡不住误读，只能靠作者直接修改和历史里的思考过程定位。
  - DeepSeek 真实运行时，AI 提出、作者没接话的点子会大量进入"悬而未决"，两轮对话就有十余条。是否要让记账更克制，等作者用一段时间再定。
  - 文档整份放进聊天上下文，变长后靠预算截断，还没有按相关度召回。
