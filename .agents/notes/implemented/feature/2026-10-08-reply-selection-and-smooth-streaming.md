# Agent Note: 回复可跨段选中，聊天区只构建可见消息，流式内容按块冻结排版

Status: implemented

## Problem

作者试用时提出两个问题：

- **选不过段落**：一条回复里只能在单个段落内拖选，Codex、DeepSeek Harness 都能一路拖过多段。原因是回复按 Markdown 块逐个画成独立的 `RichText`，而 mygo 的选区以单个文本元素为单位，不支持跨元素。
- **流式输出时滚动卡顿**。

用 `desk/perf_test.go` 的基准量了一帧的耗时（无界面测试器，软件光栅，回复流式写到约 800 字）：

| 场景 | 改动前 |
|---|---|
| 空会话，流式回复 | 1.3 ms |
| 20 轮历史，流式回复 | 5.5 ms |
| 60 轮历史，流式回复 | 15.8 ms |

性能分析显示，耗时随历史线性增长，大头在布局：每帧都把所有历史消息重新构建、重新排版。Markdown 解析只占约 1.5%。

## Decision

- **聊天区是虚拟列表**：`desk/chat.go` 的 `chatList` 用 mygo 的 `ui.List`，只构建可见的行。
  - 行是消息事件；空会话时有一行开场，一轮进行中时末尾有一行流式内容。行的键是事件 ID。
  - `FollowEnd` 让列表停在底部时跟随新内容；作者往上滚就不再跟随，滚回底部又恢复。
  - 发送、重试、完成时调用 `ScrollToEnd`；切换会话时重置 `ListState`。
> 下面「回复文字连成一个文本」「流式内容冻结排版」两条和 Markdown 解析缓存，已由 mygo 的 `ui/markdown` 取代，见[回复和摘要的 Markdown 改用 mygo 的 ui/markdown](../architecture/2026-10-19-markdown-on-mygo.md)；虚拟列表和复制全文仍照这里。

- **回复文字连成一个文本**：`mdDraw` 把相邻的段落、标题和纯文本列表合成一个可选中的 `RichText`。
  - 块之间空一行。文本引擎每行至少是基础行高，所以段落间距只能是一整行，不能更小。
  - 列表项以"•"或"1."开头，嵌套一层多缩进一个全角空格。
  - 引用、代码块、表格，以及含这些内容的列表，仍然单独成元素，选区在它们那里断开。
- **复制全文**：每条回复下有"复制全文"按钮，复制 Markdown 原文，粘到别处结构还在。
- **流式内容冻结排版**：一个文本的排版耗时和它的长度成正比，而写完的部分内容不变，排版结果可以复用。
  - `liveMarkdown`：写完的块合成一个文本，正在写的最后一块单独一个。两块之间用上边距补出原本该有的空行，回复结束后整条合成一个文本。
  - 思考过程流式期间按最后一个换行拆成两段，并且暂不设为可选中（可选中的文本每次内容变化都要重灌整段文字）；结束后恢复为一段可选中的文本。
- Markdown 解析结果仍按全文缓存，上限 256 条。

改动后同一基准：

| 场景 | 改动后 |
|---|---|
| 空会话，流式回复 | 2.6 ms |
| 20 轮历史，流式回复 | 2.2 ms |
| 60 轮历史，流式回复 | 2.1 ms |
| 20 轮历史，流式思考过程 | 2.9 ms |

## Alternatives considered

- **块级冻结 Markdown 解析（Streamdown、Incremark 的做法）** — 业界流式 Markdown 的主流优化：写完的块只解析一次，每帧只重解析最后一块。Go 没有现成的库（`dbohdan.com/strument` 的 smd.js 移植在 `internal/` 下，不能导入），自己在 goldmark 上做约 50 行。不做的原因是实测解析只占约 1.5%，排版才是大头。冻结的思路用在了排版上。
- **一整条回复始终画成一个文本，流式时也是** — 实现最简单，流式时也能跨段选中。但实测 20 轮会话下流式每帧涨到 25 ms，思考过程流式每帧 27 ms，比改动前还慢得多，因为每来一个字整条回复都要重新排版。
- **保留逐块元素，在 mygo 里实现跨元素选区** — 列表能保留悬挂缩进，跨消息拖选也有可能做到。但这要给上游加一套跨元素的选区模型，工作量大一个量级；作者确认只需单条回复内跨段选中，外加复制全文按钮。
- **流式刷新节流到每秒 20～30 帧** — 对延迟不敏感，实现也简单。但 `Invalidate` 本来就只是请求下一帧，测得每帧 2～3 ms 时节流没有收益，就没做。

## Consequences

- **收益**：每帧耗时不再随会话长度增长；流式内容在作者停在底部时自动跟随；整条回复可以拖选，也能一键复制原文。
- **代价**（前两条随改用 mygo 的 `ui/markdown` 已不存在）：
  - 列表项没有悬挂缩进，换行后的文字从左边缘开始。
  - 段落间距是一整行，比原来的块间距疏。具体疏密留到体验调整时再定。
  - 回复流式期间，选区不能跨过"写完的部分"和"正在写的那块"之间的边界。
  - 一个很长且没有换行的段落仍然会在流式时整段重新排版。
- **测量口径**：基准跑在无界面测试器上，用的是软件光栅；真实窗口用 GPU 绘制，绝对值会不同，但"随历史线性增长"这个结构性问题和它的修复与绘制方式无关。
