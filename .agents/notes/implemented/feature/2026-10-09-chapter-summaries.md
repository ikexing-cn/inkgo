# Agent Note: 章节摘要与起草时的前情提要

Status: implemented

## Problem

[AI 辅助写作](2026-10-08-ai-assisted-writing.md)起草一章时只看到上一章结尾和本章已写的部分。写到十几章以后，更早的伏笔、人物去向，AI 都不知道，起草容易前后矛盾。该篇已把"前文摘要"列为 AI 开始忘事时的后续。

作者 2026-10-08 夜里授权连夜推进，方案由 agent 决定，作者次日验收。

## Decision

### 存放

- 每章可以有一份摘要，和正文放在一起：`章名.summary.json`（`workspace.Summary`），随章节移动、进回收站、恢复。
- 内容是：
  - 摘要文字；
  - 生成时正文的哈希（`ProseHash`，按存盘时的正文、去掉首尾空白计算）；
  - 字数；
  - 谁写的：模型名，空表示作者；
  - 时间。
- 正文的哈希和摘要记下的不同，摘要就"可能过时"（`Stale`）。
- 严格按 JSON 读，未知字段报错。写空文字等于删除。

### 生成

- 作者离开一章时，满足以下全部条件，就把这一章排进后台队列（`leaveChapter`）。离开包括换章、离开正文页、关掉作品。
  - 这一章这次打开期间存过正文；
  - 正文不少于 200 字（`writing.MinSummary`）；
  - 摘要缺失，或者摘要是 AI 写的并且已经过时。
- 作者自己写的摘要永远不会被自动覆盖。正文变了只标"可能过时"。
- 队列一次只跑一章，用写作模型、不推理（`Writer.Summarize`），两分钟超时。它不占起草和改写的通道，作者照常写。
- 摘要回来时，如果作者已经为同一版正文写了摘要，丢弃 AI 的那份。
- 模型给的摘要不以句末标点（。！？…”」』））收尾，就当作没写完，报错、不存。实测中 DeepSeek 偶尔会在半句后接一串 `(function(){})` 就结束。
- "模型设置"里有开关"改完一章后更新摘要"，存在 `.writer/desk.json` 的 `no_auto_summary`，默认开。

### 本章摘要折叠区

- 和章纲在同一行，点开后在这一行下面展开。标题会显示状态："本章摘要""本章摘要 · 还没有""· 正在生成""· 可能过时"。
- 下方一行写明来源：
  - AI 写的：显示模型和时间；
  - 作者写的：显示"你写的"；
  - 正文改过了：提示过时；
  - 上次生成失败：显示原因。
- 作者可以直接改。改过的内容在下次保存时存为作者的摘要，按当时的正文算哈希。
- "生成摘要/重新生成"随时可点。正文不到 200 字时按钮不可用，并说明原因。
- 空章节（没有正文也没有摘要）不显示这个切换，免得新章节一打开就是一块空框。
- 保存模型设置时清掉"上次生成失败"。没选模型而失败的章，在选好模型后不应还挂着旧错误。

### 起草时的前情提要

- 只有起草带前情提要。它在设定之后、章纲之前加一段"【前情提要】"，按树的顺序列出本章之前各章的摘要，每章一行"《章名》摘要"。
- 过时的摘要也用。
- 从离本章最近的往前放，总共不超过 4000 字，也受上下文预算限制。
- "AI 看到了什么"写明前情提要几章、其中几章正文改过、摘要可能过时。
- 起草弹窗里：
  - 前面有章节缺摘要时，提示"前面有 N 章还没有摘要"，给"补齐摘要（N 次调用）"按钮。点了之后显示补齐进度。
  - 都有摘要时，写明"起草时 AI 会读前面 N 章的摘要，接上前情"。
- 打开作品时不自动补摘要，免得没打招呼就花钱。

2026-10-14 起 AI 可以整个关掉（见[可以整个关掉 AI](2026-10-14-disable-ai.md)）：关着时摘要框不显示，离开改过的章节也不排摘要；正在写的摘要停下，不算失败，原来的摘要不变。

## Alternatives considered

- **摘要放在 `.writer` 缓存里** — 它不算作品内容，坏了可以重建。但重建要花钱，作者改过的摘要也会丢；摘要本来就是作者可以读、可以改的提纲式内容，跟着作品走更合适。
- **起草前临时生成缺的摘要** — 不用后台任务，摘要永远最新。但起草要先等 N 次调用，章数多时要等很久，也是没打招呼就花钱。
- **全文分层摘要（卷摘要、全书摘要）** — 几百章也放得下。但先要有章摘要；卷摘要等章数多到放不下时再做。
- **续写和改写也带前情提要** — 更不容易矛盾。但续写要快、每次都调用，多几千字输入就慢且贵；改写只改一段，前后文已经够了。
- **用全选代替占位字给新章节命名**（见下） — 和系统文件管理器一致。但 mygo 的输入框只在 Tab 进入时全选，没有公开的全选接口；留空加占位字效果相同，回车也能直接用默认名。

## Consequences

- 每章多一个可选的 `.summary.json`；旧作品没有它照常打开。
- 自动摘要按"离开改过的章节"计费，每次一个不推理的调用；作者可以关掉。
- 摘要可能过时：AI 写的会在下次离开时重写，作者写的只提示。起草仍用过时的摘要，并在"AI 看到了什么"里说明。
- 一章超出上下文预算时，摘要只依据前面一段。2026-10-14 起界面上说了（见[审查后的一批修正](../bug-fix/2026-10-14-review-fixes.md)）：`.summary.json` 多一个可选的 `read`（模型拿到了前多少字，读全了不写），标题写「本章摘要 · 不完整」，下面一行末尾加「仅依据前 9000 字」，悬停说「后文超出上下文预算，可在设置中提高预算」（文案作者 2026-10-14 确认）。带 `read` 的文件，旧版本的程序读不了。
- 起草对话框里「前面有 N 章还没有摘要」原来每帧给每一章读一次盘（300 章一帧 7.9 秒），2026-10-14 改成打开时算一次、补齐做完再算一次。
- 顺带修了一处命名问题：新建章节或文件夹时，标题框留空，并用灰色占位字显示"新章节"。之前框里预填"新章节"、光标在末尾，作者直接打字会变成"新章节第三章"。标题留空提交时用占位的名字，重命名已有章节时留空则保持原名。
- 2026-10-09 用 kimi-cu 在真实程序里走了一遍，模型是 DeepSeek（`deepseek-flash`，摘要不推理，起草用默认等级）：
  - 没选写作模型时离开章节：折叠区显示"上次生成失败：还没有选择写作模型…"。选好模型、保存后，这条提示消失（本次修正）。
  - 第一章 231 字的摘要，几秒内写好，约 210 字，事件顺序和伏笔都对。初版规则让模型在末尾另列"悬念/人物/地点/物件"清单，改成"写进叙述里，不另列清单"后，连跑 4 次都没有再出现。
  - 第二章按章纲起草 300 字：写出了第一章摘要里的青石板、敲击声、工具箱和井边，衔接自然。
  - 起草弹窗的"补齐摘要"真实补了第二章。其中一次输出在半句后接了 `(function(){})`，于是加了句末标点检查。

## Testing

- `workspace/summary_test.go`：摘要写下再读回，过时判断，随章节移动、进回收站、恢复，写空即删除。
- `writing/summary_test.go`：
  - 摘要请求不推理，带章名不带 ID，去掉首尾空白；正文不足 200 字报错；没写完的摘要报错；
  - 起草带前情提要，按顺序，过时的写进清单；
  - 超过上限时保留最近的几章；
  - `Unsummarized` 只列够长且没有摘要的章，并数出已有摘要的章。
- `desk/summary_test.go`：
  - 没改过的章节不生成；改过的离开后生成；
